                  SAVED PROFILE AND SCRIPT STORAGE


Abstract

   Where the configurator keeps user work: the script source files, the
   database that indexes them, and the record format both databases
   share.

   This is what a replacement must read if existing user profiles are to
   survive. The scripting language itself is in script-bytecode.txt and
   the download path to the driver is in ioctl-surface.txt section 5a.

   Everything here is read out of the Ghidra database for wishd201.exe.
   Statements not directly supported by an instruction or a byte are
   marked INFERENCE.

1.  Files And Locations

   The base directory is the configurator's own location. cfg_GetBaseDir
   calls GetModuleFileNameA on the running module and strips the file
   name, so everything lives beside wishd201.exe rather than in a user
   profile or a shared data directory.

   +---------------------+--------------------+------------------------+
   | Path                | Mode               | Contents               |
   +=====================+====================+========================+
   | <exedir>\scripts\   | directory          | *.ac script sources    |
   | <exedir>\script.db  | rb+                | index of known scripts |
   | <exedir>\script_n.db| wb                 | rebuild temporary      |
   | <exedir>\active.db  | rb                 | which scripts are      |
   |                     |                    | assigned and active    |
   +---------------------+--------------------+------------------------+

   Paths are assembled by cfg_BaseDirPath for the databases and
   cfg_ScriptsDirPath for anything under scripts.

   Configuration that is not script related lives in the registry under

       Software\Wish Technologies\Adaptoid

   which is the user-mode side of the same key the driver reads
   VirtualDevices from; see hid-descriptor.txt section 3.

2.  Script Source Files

   Scripts are ORDINARY TEXT, not a binary or proprietary container. The
   directory is scanned with the mask *.ac, so that is the extension.

   A newly created script is seeded with

       // Adaptoid Script

       main() {}

   and the configurator also carries fragments used to generate handler
   stubs, including "int rumble", "int stick_", "int button_" and the
   "on_" handler prefix. INFERENCE: the UI can write handler skeletons
   into a script from templates rather than requiring the user to type
   them. Not established.

   Because the sources are plain text, they are the durable artefact. The
   databases below are a CACHE and an index over them, not the primary
   store, which means a replacement can ignore both and simply read the
   .ac files if it does not need the assignment state.

   RESOLVED. The INFERENCE above about handler skeletons is confirmed and
   is in fact the whole editing model: the configurator has no separate
   settings structure, and generates and re-parses script text for every
   control in the UI. The file name itself is structured, as
   <game>--<field>--<field>.ac, and a block of // tag = value line
   comments at the top of each script carries the game metadata. Both are
   documented in configurator-architecture.txt sections 1 and 4.

3.  The Record Format

   script.db and active.db share one format: a flat stream of
   tag-length-value fields. cfg_DbReadRecord at 004010c0 is the reader
   and cfg_DbWriteField at 004015f0 the symmetric writer.

   Every field is

       tag    1 byte
       len    1 byte
       data   len bytes

   The single length byte caps any field at 255 bytes, which matters for
   long file names and for the string lists.

   Two tags are control rather than data:

       0x33   end of record
       0x32   end of file

   Both are written with a length of zero. Any tag not in the table in
   section 4 is a hard error; the reader cannot skip an unknown field
   because without a type it does not know whether the payload is a
   pointer it would later have to free.

   An in-memory record is 13 dwords. cfg_DbRecordInit zeroes it and
   cfg_DbRecordFree releases the members that were heap allocated.

4.  Field Tags

   SETTLED. All thirteen fields are identified. The mapping was closed from
   two directions that agree: cfg_DbWriteScriptNode (00407b60) passes the
   record base straight to cfg_ScriptReadHeaderTags, so fields 3 to 10 ARE
   the parsed // tag = value header block; and a live script.db from an
   installed copy confirms the payloads.

   +------+-------+---------+------------------------------------------+
   | Tag  | Field | Reader  | Meaning                                  |
   +======+=======+=========+==========================================+
   | 0x3D | 0     | string  | script .ac file name, the table key      |
   | 0x3E | 1, 2  | fixed   | last-write FILETIME, low then high       |
   | 0x46 | 3     | string  | game_name                                |
   | 0x47 | 4     | string  | game_dir                                 |
   | 0x48 | 5     | string  | game_exe                                 |
   | 0x49 | 6     | string  | game_prod                                |
   | 0x4A | 7     | fixed   | game_size, decimal text via crt_atoi     |
   | 0x4B | 8     | strlist | game_regexe, repeatable                  |
   | 0x4C | 9     | strlist | game_regdir, repeatable                  |
   | 0x50 | 10    | string  | driver_version                           |
   | 0x5B | 11    | fixed   | last-launched sequence number, active.db |
   | 0x5C | 12    | fixed   | port assignment bitmask, active.db       |
   +------+-------+---------+------------------------------------------+

   The three readers behave differently and a parser must match them:

       string   allocate len+1, read len bytes, NUL terminate
       fixed    read len bytes into a fixed buffer in the record
       strlist  allocate an 8-byte node {string, next}, read the string,
                and PREPEND it, so repeated tags build a list in reverse
                order of appearance

   THE TWO DATABASES USE DIFFERENT SUBSETS. script.db is a cache of the
   script header blocks: fields 0, 1, 2 and 3 to 10. active.db records
   assignments: cfg_SaveActiveDb writes fields 0, 5, 11 and 12 only.

   Field 11 is the value cfg_LaunchGame stamps from an incrementing counter,
   so it orders scripts by when their game was last launched;
   cfg_ScanScriptDir tracks the maximum on load to resume the sequence. Field
   12 is a bitmask with bit N set when the script is assigned to controller
   port N, maintained by cfg_AssignScriptToPort.

   A record written by cfg_DbWriteRecord OMITS any field that is null or
   zero, so most records are short. Both control tags are written with a
   length of zero: 0x33 ends a record, 0x32 ends the file.

4.1.  A Real Example

   From an installed copy, active.db is 26 bytes in full:

       3d 0e  "@--TRON 2.0.ac"      field 0, script name
       5c 04  01 00 00 00           field 12, port mask = port 0
       33 00                        end of record
       32 00                        end of file

   and a typical script.db record is

       3d 09  "@--PSX.ac"           field 0, script name
       3e 08  5e 55 26 e7 8d 04 c9 01   fields 1,2, FILETIME
       50 05  "2.0.0"               field 10, driver_version
       33 00                        end of record

   Every record in that file carries exactly those three tags, because all 24
   scripts in the install are common "@--" scripts with no game bound. The
   0x50 payloads are "2.0.0" except for Sample Absolute Mouse.ac, which is
   "1.3.175" - matching the driver_version line in the .ac file itself.

   NOTE a quirk visible in that file: script.db BEGINS with a 32 00 pair, an
   end-of-file marker, before its first record. cfg_DbCreateNew writes it
   into a freshly created database, and the rebuild path appends records
   after it rather than overwriting it. A reader that stops at the first
   0x32, as cfg_DbReadRecord does, therefore sees an EMPTY database on the
   first read of that file. INFERENCE: this is why the configurator tolerates
   a full rebuild so readily - the cached index is cheap to discard. Not
   established; the rebuild path was not traced far enough to confirm the
   leading marker is always present.

5.  Scanning And Rebuilding

   cfg_ScanScriptDir at 00407690 reconciles the directory with the
   database on startup and whenever the directory changes. The
   configurator watches for that with FindFirstChangeNotificationA, so
   editing a .ac file in another editor is noticed without a restart.

       1  enumerate <exedir>\scripts\*.ac, recording each file name and
          its last-write FILETIME into an in-memory table
       2  open script.db and read it record by record
       3  for each record, compare the stored FILETIME against the file
          on disk
       4  unchanged records are kept as they are
       5  the first changed or missing record switches the scan into
          rebuild mode: everything read so far is copied into
          script_n.db and the rest of the scan writes there
       6  on success, delete script.db and rename script_n.db over it
       7  finally read active.db into a second table

   The rebuild is all-or-nothing and goes through a temporary file, so an
   interrupted scan leaves the original script.db intact. That is worth
   preserving.

6.  Consequences For The Replacement

   -  The .ac sources are the real user data. Any replacement should read
      and write those, and treat the databases as a rebuildable cache.

   -  Storing everything beside the executable does not work on a modern
      Windows install, where Program Files is not writable by a normal
      user. A port must move the data to a per-user location, and should
      migrate an existing installation's files rather than stranding
      them.

   -  The record format is trivially portable: byte tags, byte lengths,
      no alignment, no pointer-sized fields. It survives a 64-bit port
      untouched. Whether it is worth keeping is a different question,
      since a replacement that regenerates its own index has no reason to
      keep a 255-byte field limit.

   -  RESOLVED. All thirteen fields are identified; see section 4. The
      method was the one suggested here - dump a real script.db and match
      it against the .ac files - combined with reading
      cfg_DbWriteScriptNode, and the two agree.
