Adaptoid Reverse Engineering                                 Analysis Note
wishk201.sys                                                 2001 driver


                      DRIVER DATA STRUCTURES


Abstract

   The layout of every structure wishk201.sys carries, and how they nest. The
   centrepiece is the per-device extension: a single 0x1800-byte block that
   holds nearly all driver state, including the input poll slots, the force-
   feedback engine and the script interpreter.

   This note exists because the extension IS the driver. Almost every routine
   takes a pointer to it, and until its fields were named the decompiled code
   was an undifferentiated stream of hex offsets. It also records the Windows
   and USB structures the driver uses, since the offsets it hard-codes only
   make sense against those layouts.

   Everything here is read out of the Ghidra database for wishk201.sys. Where
   a Windows or USB structure is quoted it has been checked against the
   headers in the Windows 2000 DDK; those checks are called out. Field sizes
   derived only from the distance to the next field in use are marked
   INFERENCE, because that is weaker evidence than a field being read.

1.  How The Extension Is Reached

   wishk201.sys never calls IoCreateDevice for its functional device object.
   It is a HID minidriver: it registers with HidRegisterMinidriver and
   hidclass creates the FDO, sizing the extension from the
   DeviceExtensionSize field of the registration block.

   That produces TWO levels of extension, and confusing them makes every
   offset wrong:

       DEVICE_OBJECT
         +0x28 DeviceExtension  ->  HID_DEVICE_EXTENSION
                                      +0x00 PhysicalDeviceObject
                                      +0x04 NextDeviceObject
                                      +0x08 MiniDeviceExtension
                                              |
                                              v
                                    _ADAPTOID_DEVEXT, 0x1800 bytes

   drv_AddDevice reads all three HID_DEVICE_EXTENSION members at 00012372 and
   caches them in its own extension at +0x14, +0x18 and +0x1c, which is why
   routines reach the lower driver as DevExt->NextDeviceObject rather than
   walking back up.

   THE SIZE IS CERTAIN. drv_AddDevice zero-fills the block with a
   0x600-iteration dword loop before touching anything else, and no
   instruction anywhere in the image references an offset at or beyond
   0x1800.

   IT IS ALSO DECLARED, not merely implied. drv_DriverEntry builds a
   HID_MINIDRIVER_REGISTRATION on its stack and sets DeviceExtensionSize to
   0x1800 before calling HidRegisterMinidriver. The size is therefore
   confirmed from both ends: the declaration hidclass acts on, and the zero-
   fill the driver performs on what it gets back.

   SCRIPTSTATE IS NOT A COUNTER. IOCTL fn 0x83C shows it as a small state
   machine, and drv_BuildJoystickReport tests it for >= 0 to decide whether
   script-written stick values override the raw controller:

       -1   no script loaded; the value drv_AddDevice writes
        0   script loaded and idle
       >0   scheduler passes in flight, counted by drv_ScriptSchedulerDpc
       -2   a load is in progress
       -3   accepted by the load path alongside 0 and -1

   fn 0x83C permits a load only when the value is 0, -1 or -3, otherwise it
   writes -2 and returns STATUS_DEVICE_BUSY. After loading it writes
   (CodeCount != 0) - 1, so 0 for a real script and -1 for an unload.

3.  Embedded Structures

3.1.  ADAPTOID_POLL_SLOT, 0x14 bytes, two of them at 0x2F0

       +0x00  CancelLatch   non-zero while drv_PollStop is cancelling
       +0x04  Irp
       +0x08  Urb           URB_BULK_OR_INTERRUPT_TRANSFER *
       +0x0C  Buffer[5]     the raw controller bytes
       +0x11  Active        slot should have a read outstanding

   TWO SLOTS, established three ways: drv_PollStart submits exactly slots 0
   and 1, drv_PollStop scans with a bound of 8 over 4-byte entries, and
   drv_PollComplete matches the completing IRP against two slots only. Two
   slots end the array at 0x318, exactly where PollStopMask begins.

   CancelLatch is how the submit and cancel paths agree on ownership: whoever
   finds it clear frees the IRP and URB, so they are never double-freed.

3.2.  ADAPTOID_EFFECT_SLOT, 0x38 bytes, 32 of them at 0x448

       +0x00  Type            0x10 constant, 0x20 ramp, 0x30-0x34
                              periodic, 0x40 condition
       +0x04  Running
       +0x08  StartTime       64-bit, in 1/64-second ticks
       +0x10  Duration        -1 means infinite
       +0x14  AttackLevel     }
       +0x18  AttackTime      }  a DirectInput envelope
       +0x1C  FadeLevel       }
       +0x20  FadeTime        }
       +0x24  AxisBlockLength
       +0x28  Axis[2]         ADAPTOID_EFFECT_AXIS, 8 bytes each

   Both the base and the stride are certain and independently sourced:
   drv_EffectSlotActive indexes as devext + 0x448 + slot * 0x38, and
   drv_BuildJoystickReport walks the same array with a 0xE-dword step bounded
   by 0x20.

3.3.  ADAPTOID_EFFECT_AXIS, 8 bytes

       +0  Magnitude   signed        +1  Offset   signed
       +2  Phase       scaled /36000 +4  Period   in ticks

   FOR EFFECT TYPE 0x40 THE SAME EIGHT BYTES ARE REINTERPRETED as a
   DirectInput CONDITION block - centre, positive and negative coefficients,
   saturation, dead band and a computed output at +6 - driven by the live
   stick position rather than by time. The pre-pass at the top of
   drv_EffectEvaluate computes +6 from CurStickX / CurStickY and the main
   switch reads it back.

3.4.  ADAPTOID_EFFECT_TICK, 0x1C bytes, 96 of them at 0xB58

       +0x00  Pulse         motor on for this tick; this bit ships
       +0x04  Intensity
       +0x08  FilteredX     5/6 decay low-pass
       +0x0C  FilteredY
       +0x10  Accumulator   delta-sigma, emits a pulse past 100
       +0x14  DitherBurst
       +0x18  TuneCounter

   96 entries of 0x1C bytes span 0xA80 and end exactly at 0x15D8 where the
   tuning values begin. The engine runs ahead of real time, then packs 32
   consecutive Pulse bits into the four payload bytes of vendor command 0x36.
   Magnitude becomes pulse DENSITY through the accumulator, which is how a
   proportional effect drives an on/off motor.

3.5.  ADAPTOID_SCRIPT_THREAD, 0x24 header plus stack

       +0x00  Link        on ReadyThreadList or FreeThreadList
       +0x08  ThreadId    from NextThreadId
       +0x0C  Pc
       +0x10  Blocked     cleared by _wake
       +0x14  ArgCount    dwords copied into the stack area
       +0x18  WakeTime    64-bit, the scheduler sort key
       +0x20  StackSize
       +0x24  stack

   Allocated as StackSize * 4 + 0x24, with StackSize CLAMPED TO A MINIMUM OF
   8 dwords. Threads are pooled: drv_ScriptThreadAlloc pops FreeThreadList
   and reuses a node whose stack is big enough, otherwise pushes it back and
   allocates fresh - so a reused node may be larger than requested.

3.6.  ADAPTOID_SETUP_PACKET, 6 bytes at 0x3A4

       +0  bmRequestType   0x40 vendor OUT, 0xC0 vendor IN
       +1  bRequest
       +2  wValue
       +4  wIndex

   This is a USB setup packet, not a private command format.
   drv_SendVendorRequest copies bRequest, wValue and wIndex straight into a
   URB_CONTROL_VENDOR_OR_CLASS_REQUEST and derives TransferFlags from bit 7
   of bmRequestType. For the effect tick the 32-bit motor bitmap rides in
   wValue:wIndex with no data stage at all.

3.7.  ADAPTOID_REPORT_NODE, 0x18 bytes

       +0x00  Link      queued on QueuedReportList
       +0x08  Length    payload length, not counting itself
       +0x09  Data[15]  report ID followed by the report body

   Allocated only when no read IRP is waiting. 15 payload bytes is enough for
   the largest report the driver builds, the 13-byte keyboard one.

3.8.  DRV_REMOVE_LOCK, 0x20 bytes

       +0x00  IoCount      initialised to 1
       +0x04  Removed
       +0x08  RemoveEvent  KEVENT
       +0x18  AllocateTag

   A hand-rolled equivalent of the DDK IO_REMOVE_LOCK. drv_LockInitialize,
   drv_LockAcquire, drv_LockRelease and drv_LockReleaseAndWait mirror
   IoInitializeRemoveLock, IoAcquireRemoveLock, IoReleaseRemoveLock and
   IoReleaseRemoveLockAndWait, down to the four-argument init and the (Lock,
   Tag) shape on the rest. drv_LockAcquire returns STATUS_DELETE_PENDING once
   Removed is set.

   The six-character strings near the call sites - PolRst, HrrPend, VenSub
   and the rest - are the Tag argument, NOT pool tags. The pool tag this
   driver actually uses is 'Wish' (0x68736957) on every
   ExAllocatePoolWithTag.

4.  The Control Device Extension

   ADAPTOID_CDO_EXT, 0x78 bytes, on the singleton control device
   \Device\Wish_NA1 created by drv_CreateControlDevice with device type
   0xB98C - the same value the private IOCTL codes encode.

       +0x00  Magic[3]           3E178AA3 7625F013 ED739374
       +0x0C  DeviceObject       back pointer
       +0x10  Deleting           set during teardown
       +0x14  OpenCount          handles open on \.\Wish_NA1
       +0x18  CommandBlock[0x40] the SDK simple-interface joybus block
       +0x58  SwapBytes          byte-swap the block on the way out
       +0x5C  EventCount         capped at 99
       +0x60  EventList          LIST_ENTRY
       +0x68  WaiterList         LIST_ENTRY, IRPs waiting for an event
       +0x70  DeliveryInProgress
       +0x74  SpinLock

   Every dispatch wrapper tests the magic to recognise this device. The queue
   is DRIVER-WIDE, not per handle and not per adapter: every controller posts
   into it and any waiter can receive any event.

   CommandBlock ends at exactly 0x58, where SwapBytes begins, which is the
   same kind of arithmetic confirmation as the poll slots and the effect
   ring: a 64-byte field placed at 0x18 lands precisely on the next field in
   use.

   A 64-byte WriteFile on the control device lands in CommandBlock and is
   walked by drv_ProcessCommandBlock; a 64-byte ReadFile copies it back. That
   is the transport behind the SDK simple interface recorded in ioctl-
   surface.txt section 3.1.

5.  Windows And USB Structures

   The driver hard-codes offsets into these, so the replacement has to match
   them or abandon the offsets entirely. All were first reconstructed from
   the binary and then checked against the Windows 2000 DDK headers
   (inc/ddk/wdm.h, inc/ddk/hidport.h, inc/api/usb.h). Every reconstruction
   matched.

   TWO SIZES ARE CONFIRMED BY THE DRIVER ITSELF, independently of any header.
   drv_SendIoctlSync sizes its packet as StackSize * 0x24 + 0x70, which is
   the driver stating sizeof(IRP) and sizeof(IO_STACK_LOCATION). And
   drv_PollSubmit reaches the poll pipe handle as *(devext+0x290) + 0x18,
   which is Pipes at 0x10 plus PipeHandle at 0x08 inside
   USBD_PIPE_INFORMATION.

6.  Corrected Function Arities

   TWENTY functions had a declared parameter count that did not match their
   stack purge. Until each was fixed the decompilation silently dropped
   arguments, which in several cases hid the whole point of the routine -
   drv_SendVendorRequest appeared to take no completion callback, so the
   vendor path looked like it had no continuation.

   Every signature in the database is now verified against the RET immediate
   of the function it describes.

   | drv_CompleteNotificationIrps     | 1     | 2    | an unused second argument          |
   | drv_ProcessCommandBlock          | weak  | 3    | control extension, block, pass     |
   +----------------------------------+-------+------+------------------------------------+

   drv_N64Transaction is the one whose correction changes meaning rather than
   just readability. It was recorded as taking a single buffer that held the
   command on entry and received the reply. It does not: the command buffer
   and the reply buffer are SEPARATE arguments, five and six. Every caller
   passes a distinct local for the reply.

   HOW THEY WERE FOUND. The first thirteen came from reading call sites. The
   remaining six came from a mechanical sweep comparing each function's
   declared parameter bytes against the RET immediate in its own epilogue -
   which is the check that should have been run first. A wrong (void)
   signature is invisible to any search for suspicious-looking prototypes,
   because there is nothing suspicious about it.

7.  Unreferenced Regions

   122 bytes of the extension are touched by nothing but the zero-fill. These
   are worth recording because a replacement can drop them, and because
   proving a region dead is as much a result as naming it.

   +-------------------+-------+------------------------------------------------------+
   | Range             | Size  | Evidence                                             |
   +===================+=======+======================================================+
   | 0x15F8..0x163F    | 72    | no scalar in range anywhere in the image; the        |
   |                   |       | used offsets step 0x15F4 -> 0x1640                   |
   | 0x03AE..0x03E3    | 54    | as above, and unreachable indirectly: the only       |
   |                   |       | devext transfer buffer is ProbeReply with            |
   |                   |       | length 4; all other vendor requests use stack        |
   | 0x0330            | 4     | written once with 0x300000FF, never read             |
   | 0x17F4            | 4     | read once, never written; permanently zero           |
   | 0x17F8            | 4     | read once to free it, never assigned; the            |
   |                   |       | ExFreePool beside it never executes                  |
   +-------------------+-------+------------------------------------------------------+

   The 72-byte hole ends exactly on a 64-byte boundary, which would place
   ScriptState and the lock guarding it at the start of a cache line. That is
   consistent with deliberate padding against false sharing and equally
   consistent with members deleted during development. INFERENCE either way;
   nothing in the binary distinguishes them.

7.1.  Residual Decompiler Artefacts

   After typing, 14 of the 144 driver functions still show synthetic
   variables. They are recorded here so nobody spends time trying to type
   them away: in each case the database is correct and the decompiler's
   rendering is the limitation.

   -  extraout_EAX / extraout_EDX, in seven functions. KeQueryInterruptTime
   -  returns a 64-bit value in the EDX:EAX pair, which is declared
   -  correctly. Where the result is consumed after a branch, the decompiler
   -  splits the pair into two synthetic halves instead of carrying one
   -  64-bit value.

   -  unaff_EDI, in drv_ScriptScheduler. The KeSetTimer call passes a Timer,
   -  an 8-byte DueTime and a PKDPC, which both the push sequence and the RET
   -  0x10 confirm. The decompiler mis-groups the 8-byte argument and renders
   -  the Dpc as CONCAT44 material.

   -  in_stack_NNNNNNNN, in eight functions. The compiler reuses incoming
   -  parameter slots as scratch, and drv_ScriptThreadAlloc actually writes a
   -  clamped value back over its own argument. The decompiler then treats
   -  the slot as a phantom parameter beyond the declared arity.

   None of these indicates a wrong signature. Every function in the driver
   has been checked against the RET immediate of its own epilogue, and all
   146 agree.

8.  What Changes On 64-bit

   NONE OF THE OFFSETS IN THIS NOTE CARRY OVER. Every pointer, LIST_ENTRY,
   handle and KEVENT widens, and so does every Windows structure the driver
   indexes. The portable content is the FIELD ORDER AND MEANING, which is why
   these are recorded as structures rather than as offset tables.

   Specific consequences for a port:

   -  LIST_ENTRY doubles from 8 to 16 bytes. The extension holds seven of
   -  them, so the thread, event, report and device lists all move.

   -  The script thread header grows past 0x24, which changes the StackSize *
   -  4 + 0x24 allocation and the fault-record size that IOCTL fn 0x83D
   -  reports to user mode. That size is part of the user-mode contract, so
   -  it cannot be widened silently.

   -  The effect slot is currently exactly 0x38 with two 8-byte axis blocks.
   -  The axis block is all fixed-width scalars and does not grow, but the
   -  slot's alignment does.

   -  ADAPTOID_SETUP_PACKET is six bytes of fixed-width USB fields and is the
   -  one structure here that ports unchanged.

9.  Open Questions

   -  RESOLVED. The 0x328 slack on the Vars allocation is the STACK-LOCAL
   -  REGION, not padding. drv_ScriptCheckVarIndex resolves operand tag
   -  0x30000000 as a local, bounded at 199, and rewrites it to VarCount +
   -  index. 200 slots is 800 bytes against 808 allocated. A consequence
   -  worth noting: locals are per-DEVICE, not per-thread, so forked threads
   -  share them.

   -  RESOLVED for all but one. Only drv_ProcessCommandBlock still has a
   -  parameter no call site determines. Every other function in the driver
   -  now has a signature whose declared size matches its RET immediate.

   -  ScriptState value -3. The load path accepts it alongside 0 and -1 but
   -  nothing observed writes it.

   -  Extension fields 0x0004..0x000C, 0x0020..0x002B, 0x034C..0x035F,
   -  0x0370..0x0377, 0x0398..0x03A3 and 0x042C..0x0433 remain unnamed. None
   -  is larger than 20 bytes.
