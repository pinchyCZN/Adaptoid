Abstract

   Every function in wishk201.sys, grouped by subsystem. No function in
   the image carries a default FUN_ name any more, so this note is a
   complete inventory rather than a sample.

   Names are the ones in the Ghidra database. Where a function has a
   plate comment recording its evidence, that comment is authoritative
   and this note is only an index.

   Confidence is marked per entry:

       (no mark)  behaviour read directly out of the code
       [I]        name is an inference from call sites and effects
                  rather than from reading the body in full

1.  Coverage

   Ghidra reports 196 functions. That count includes import thunks and the
   two compiler helpers; the driver's own code accounts for about 147 of
   them. All are named.

   Getting there required creating 30 functions by hand. 21 came from regions
   Ghidra had left as ORPHANED INSTRUCTIONS - chiefly the dispatch wrappers,
   the accessory probe chain and the polling engine. The other nine came from
   a later sweep described in section 1.1, and were a different problem: not
   orphaned, but never disassembled at all.

1.1.  The Gap Scan, And Why Symbol Counts Lie

   A count of zero remaining FUN_ names does NOT mean a binary is fully
   covered. It means everything Ghidra found has been named. Code Ghidra
   never found is not counted, not named, and not missed.

   The check that does work is to walk the executable blocks, skip over every
   defined function body, and inspect what is left. Trim 0x90, 0xCC and 0x00
   from both ends of each gap; whatever still has bytes in it is either data
   or undiscovered code. Run against all three binaries after each had
   reached zero FUN_, this found code every time:

   +---------------+---------------+-----------+------------------------------+
   | Binary        | Functions     | Recovered | What they were               |
   +===============+===============+===========+==============================+
   | wishh201.dll  | 112 -> 137    | 25        | stdio teardown chain,        |
   |               |               |           | reached only through a       |
   |               |               |           | .CRT$XP terminator slot      |
   +---------------+---------------+-----------+------------------------------+
   | wishk201.sys  | 187 -> 196    | 9         | IoCompletion, cancel and     |
   |               |               |           | DPC routines, every one      |
   |               |               |           | pointer-only                 |
   +---------------+---------------+-----------+------------------------------+
   | wishd201.exe  | 619 -> 683    | 64        | a whole dialog procedure,    |
   |               |               |           | CRT stdio and SEH,           |
   |               |               |           | static-guard stubs           |
   +---------------+---------------+-----------+------------------------------+

   THE COMMON CAUSE is that none of the recovered functions is ever the
   target of a CALL. Each is reached through an address that is only ever
   stored: a completion routine handed to IoSetCompletionRoutine, a cancel
   routine handed to IoSetCancelRoutine, a DPC registered at AddDevice, a
   dialog procedure handed to DialogBoxParamA, a terminator pointer sitting
   in a NULL-bounded .CRT$XP table, a scope-table thunk named only in an
   EXCEPTION_REGISTRATION record. Ghidra's recursive-descent disassembler
   follows calls and jumps; it does not follow data.

   TWO DISTINCT FAILURE MODES appeared, and they need different checks. In
   wishk201.sys and wishd201.exe the bytes had been disassembled but not
   gathered into functions, so a gap scan reports them as ORPHANED
   INSTRUCTIONS. In wishh201.dll they had never been disassembled at all, so
   there were no instructions to orphan and the same report said only
   UNDEFINED BYTES. A scan that keys on orphaned instructions alone finds
   nothing in the DLL.

   The largest single recovery was cfg_GameBindingDlgProc at 0040e870 in
   wishd201.exe - 1175 bytes, the whole dialog that binds a script to a game
   executable, and the source of the game_exe, game_dir and game_name header
   tags. It had been entirely absent from the analysis.

   Most gap content is legitimately data and should stay that way: switch
   jump tables, the L"\DosDevices\..." strings, the driver's
   ExAllocatePoolWithTag tags (KeyFet, CdoIoc, HrrPend, PnpFdo, PolRst,
   PwrFdo, PwrSelf, VenSub, VenCmp), the MSVC "VC20XC00" marker, and the C++
   EH unwind funclets that belong to a neighbouring function rather than
   standing alone.

4.  The Control Device

       000103be  drv_CreateControlDevice     \Device\Wish_NA1

       00011330  drv_ControlDeviceClose
       000113b0  drv_ControlDeviceReadWrite

       00010e20  drv_ExecuteRawCommand

   drv_ControlDeviceReadWrite is the READ and WRITE path on the control
   device, and it exchanges a fixed 0x40-byte block. drv_ProcessCommandBlock
   parses that block as a sequence of packed sub-commands, each dispatched
   to drv_ExecuteRawCommand, which either emulates a Controller Pak read
   or write locally or forwards the bytes as an N64 transaction.

   This is the same 64-byte exchange the control IOCTLs fn 0x802 and
   0x803 declare, which earlier revisions of ioctl-surface.txt recorded
   as an unexplained transfer length.

8.  Script Engine

       00017310  drv_ScriptLoad
       00017b90  drv_ScriptExecute           the bytecode interpreter
       000186a0  drv_ScriptNativeCall        the builtin library
       00018640  drv_ScriptCheckVarIndex
       00017980  drv_ScriptScheduler
       000177c0  drv_ScriptThreadAlloc
       00017860  drv_ScriptThreadQueue
       00017550  drv_ScriptDispatchInput

   drv_ScriptDispatchInput is how a script hooks input. On every change
   in controller state it reads handler addresses out of the script's own
   variable array and spawns a thread for each one that holds a tagged
   code address: sixteen slots for the individual buttons at offsets
   0x00..0x3F, then +0x40 for the aggregate button word, +0x44 for the
   stick, and +0x48 and +0x4C for a pair that fire on any change and
   bracket the others. Each slot, what gates it and what arguments it
   receives are tabulated in script-bytecode.txt section 9.7.

   drv_ScriptScheduler refills the interpreter's instruction budget in
   proportion to elapsed time, capped at 100000, runs every thread whose
   wake time has passed, drains the event list and re-arms the timer.
   Exhausting that budget does not pause a thread, it kills it: see
   script-bytecode.txt section 9.3.

11. USB Transport

       000193df  drv_SendVendorRequest
       00019527  drv_SubmitVendorUrb
       00019747  drv_VendorUrbComplete

       00015f90  drv_UsbGetPortStatus
       00016010  drv_UsbResetPort
       00016080  drv_UsbCyclePort
       00015f50  drv_RecoverPort
       00019290  drv_SendIoctlSync
       00018b00  drv_SetDeviceEnable            [I]
       00018ca0  drv_SendIdleCommand            [I]

   drv_RecoverPort explains the sentinel 0xC0012345 that
   drv_PollRestartWorker tests. It reads the port status; if the port is
   connected but not enabled it issues IOCTL_INTERNAL_USB_RESET_PORT,
   and otherwise falls back to IOCTL_INTERNAL_USB_CYCLE_PORT and returns
   that sentinel. A cycle is the heavier recovery, so the sentinel is the
   signal to stop retrying.

   Two more vendor requests turn up here, beyond those in
   usb-transport.txt section 3:

       0x75  IN   firmware information, result kept at devext+0x33E
       0x32  OUT  idle and enable control, see section 9

12. Synchronisation And Deferred Work

       000158e0  drv_LockInitialize
       00015930  drv_LockAcquire
       00015970  drv_LockRelease
       000159a0  drv_LockReleaseAndWait
       00015f00  drv_IsDeviceReady
       00019670  drv_TryClaimVendorSlot
       00019960  drv_ClaimVendorSlotForIrp
       000199c0  drv_CancelVendorRequest
       00019620  drv_NextDeferredWork
       000196e0  drv_RunDeferredWork

   The lock family is a hand-rolled equivalent of IoAcquireRemoveLock: a
   reference count, a "removing" flag and an event, with
   drv_LockReleaseAndWait as the drain. drv_LockAcquire returns
   STATUS_DEVICE_NOT_CONNECTED once the flag is set.

   The deferred-work system is four flags at devext+0x434, +0x438, +0x43C
   and +0x440, each mapping to one callback. drv_NextDeferredWork returns
   the highest-priority pending one and drv_RunDeferredWork loops until
   none remain. It exists because only one vendor transfer may be in
   flight at a time, so work that arrives while the slot is busy is
   deferred rather than dropped.

13.1.  Declared Arity Was Wrong In Thirteen Functions

   Naming a function does not make its signature right. TWENTY routines in
   wishk201.sys had a declared parameter count that did not match the stack
   purge in their own epilogue, so the decompilation silently dropped
   arguments.

   This mattered more than it sounds. drv_SendVendorRequest was typed with
   two parameters instead of five, which hid the transfer length, the data
   buffer AND the completion callback - so the entire vendor-request path
   appeared to have no continuation, and the callbacks recovered from code
   gaps looked orphaned. drv_SendIoctlSync was typed as taking nothing at all
   when it takes seven.

   Every signature in the database is now checked against the RET immediate
   of the function it describes. The full list is in driver-structures.txt
   section 6.

   GENERAL LESSON: a wrong prototype is worse than a missing one, because it
   produces confident, readable, wrong output. The RET immediate of a stdcall
   function is free ground truth and should be checked before any signature
   is trusted.

   Six of them were found only by a mechanical sweep of every
   function, comparing declared parameter bytes against the RET immediate. An
   earlier pass had missed them because it looked for prototypes CONTAINING
   suspicious text - undefined types or unnamed parameters - and a wrong
   (void) signature contains neither. Sweep the invariant, not the symptom.

13.2.  Two Places The Decompiler Actively Misleads

   Both were caught only because a name that had been written down stopped
   agreeing with the disassembly. They are recorded because the same shapes
   will recur.

   A CONSTANT THAT COLLIDES WITH A FUNCTION ADDRESS. The script instruction
   budget is 100000, which is 0x186A0, and drv_ScriptNativeCall happens to
   live at 0x186A0. Ghidra therefore prints the budget's initialiser and its
   clamp as `= drv_ScriptNativeCall` in both drv_ScriptLoad and
   drv_ScriptScheduler. The DEC and CMP against zero in drv_ScriptExecute
   settle that it is a number.

   A NULL CHECK THAT LOOKS LIKE A PARAMETER COMPARISON. In
   drv_ResetAllDeviceState the decompiler renders the loop guard as `if (link
   != (undefined4 **)0x344)`. That reads as a comparison against a parameter-
   relative address, and an earlier revision named the argument Except on
   that basis. The disassembly is XOR EDI,EDI followed by LEA ECX,[ESI-0x344]
   and CMP ECX,EDI - a NULL test on the extension base recovered from the
   list link. The function processes every device and never reads its
   argument at all.

   The general shape: a folded constant in decompiler output is not evidence
   of what the constant MEANS. Where a name would encode a claim about the
   constant, read the instructions.

14. What Is Still Not Known

   Naming every function is not the same as understanding everything.
   These remain open:

   -  The firmware register semantics behind vendor requests 0x72 and
      0x74, including the probe parameters and the 0x00C6 / 0x00A6
      values. These are inside the adapter's firmware and are unlikely to
      be recoverable from the driver alone; a USB capture would settle
      them.

   -  Which accessory kind maps to accessory state 2 versus state 3.

   -  RESOLVED, and both turned out to be dead. devext+0x17F4 is read exactly
   -  once in the whole image, in drv_DispatchPnp, and is never written
   -  anywhere - so it is permanently zero and the veto it gates can never
   -  fire. devext+0x17F8 is read exactly once, to free it, and is never
   -  assigned - so it is permanently NULL and that ExFreePool never runs.
   -  See driver-structures.txt section 7.

   -  The eleven entries marked [I] above, where the name is an inference
      from call sites rather than a full reading of the body.

   -  RESOLVED. wishd201.exe is now fully named: 683 functions, zero left as
      FUN_. 270 carry a cfg_ prefix and are the application; the remainder
      are the statically linked MSVC 6 runtime, prefixed crt_, plus import
      thunks. 73 functions were created by hand - nine from orphaned
      instructions (the two window procedures, two dialog procedures, two
      worker threads and three atexit callbacks) and a further 64 from the
      gap scan in section 1.1, among them a THIRD dialog procedure,
      cfg_GameBindingDlgProc. The architecture is written up in
      configurator-architecture.txt.

   -  RESOLVED. wishh201.dll, the third binary, is now in decomp/ and fully
   -  named: 137 functions, zero left as FUN_. It is a system-wide WH_SHELL
   -  hook DLL for game-launch detection, and its mechanism is read rather
   -  than inferred. See configurator-architecture.txt section 8 and known-
   -  defects.txt section 5.
