Adaptoid Reverse Engineering                                 Analysis Note
wishk201.sys                                                 2001 driver


                      HID REPORT DESCRIPTORS


Abstract

   The Adaptoid presents itself to Windows as a composite HID device:
   one physical USB device reporting a mouse, a keyboard, and a joystick
   as three separate top-level application collections. This is the
   property that lets the adapter drive any application, because the OS
   delivers genuine HID keyboard and mouse input rather than synthesized
   events injected from user mode.

   This note records where the report descriptors live in wishk201.sys,
   how one of three variants is selected at device-add time, the exact
   item stream of each, the resulting report byte layouts, and the HID
   minidriver IOCTL surface that serves them.

   Everything here is read out of the Ghidra database for wishk201.sys.
   Statements not directly supported by an instruction or a byte are
   marked INFERENCE.

1.  Driver Role

   wishk201.sys is a HID minidriver. It imports HidRegisterMinidriver
   from hidclass.sys and calls it from drv_DriverEntry at 000115f0. The
   minidriver owns the USB transport and supplies the report descriptor;
   hidclass.sys owns the HID plumbing and presents the collections to
   the rest of the system.

   That division is why the remapping is invisible to applications. The
   descriptor below is what every application sees. Nothing above the
   driver is aware that the bytes originated on an N64 controller.

   drv_DriverEntry installs its dispatch table, calls HidRegisterMinidriver
   (which replaces that table with the hidclass entry points), saves the
   replaced pointers to 00019d98..00019db4, and then installs its own
   wrappers over them. Those wrappers let one driver object serve the private
   control device and the private per-device channel alongside real HID
   traffic, which is chained through to hidclass untouched. See ioctl-
   surface.txt section 1.

2.  Descriptor Storage

   Three complete report descriptors are stored as static byte arrays at
   the start of the .data section, followed by an eight-entry selection
   table.

   +-------------------------------+----------+--------+-----------------------------+
   | Symbol                        | Address  | Length | Collections                 |
   +===============================+==========+========+=============================+
   | drv_HidReportDesc_MouseKbdJoy | 00019b40 |    185 | Mouse + Keyboard + Joystick |
   | drv_HidReportDesc_JoyOnly     | 00019c00 |     64 | Joystick                    |
   | drv_HidReportDesc_MouseKbd    | 00019c40 |    121 | Mouse + Keyboard            |
   | drv_HidReportDescTable        | 00019cc0 |     64 | 8 entries of {ptr, length}  |
   +-------------------------------+----------+--------+-----------------------------+

   The table entry is 8 bytes: a 4-byte pointer at +0 and a 4-byte
   length at +4. Contents as stored:

       index  pointer   length   descriptor
         0    00019c00      64   Joystick only
         1    00019c00      64   Joystick only
         2    00019c00      64   Joystick only
         3    00019c00      64   Joystick only
         4    00019c00      64   Joystick only
         5    00019c00      64   Joystick only
         6    00019c40     121   Mouse + Keyboard
         7    00019b40     185   Mouse + Keyboard + Joystick

   Note that no instruction anywhere in the image contains the literal
   address of any descriptor. They are reached only through this table,
   which is why a naive cross-reference search finds nothing. The two
   cross-references Ghidra reports against 00019b40 are PE section-table
   fields at 000100f0 and 000101ec, not code.

      CORROBORATION. The install directory ships three files, RPD1.bin, RPD2.bin
   and RPD3.bin, of 185, 64 and 128 bytes. Their contents are byte-for-byte
   the three descriptors above: RPD1 is the 185-byte Mouse + Keyboard +
   Joystick, RPD2 the 64-byte Joystick-only, and RPD3 the Mouse + Keyboard,
   whose 121 descriptor bytes are padded with seven trailing zeroes to 128.
   They are an independent check on the reading above and on the lengths in
   the selection table.

3.  Descriptor Selection

   The table index is (g_dwVirtualDevicesMask & 7), where
   g_dwVirtualDevicesMask is the global at 00019d68.

   drv_DriverEntry initialises it to 7 at 00011604. drv_AddDevice then
   overwrites it at 00012553 by calling drv_RegQueryDword with the value
   name L"VirtualDevices". drv_RegQueryDword (00011c3c) performs a
   RtlQueryRegistryValues REG_DWORD read against:

       \REGISTRY\Machine\Software\Wish Technologies\Adaptoid

   So the HID personality of the device is a single registry DWORD, read
   once per device arrival. Changing it requires a replug or a restart of
   the device stack; it is not renegotiated at runtime.

   Only indices 6 and 7 select distinct descriptors. Indices 0 through 5
   all resolve to the joystick-only descriptor.

   INFERENCE: the three-bit mask looks like it was meant to be a set of
   per-collection enables, but as built only two of the eight slots are
   distinct, so the low bits carry no independent meaning in this
   binary.

4.  Descriptor A: Mouse + Keyboard + Joystick

   The 185-byte descriptor at 00019b40, decoded. This is the default and
   the one that gives the adapter its unusual reach.

4.3.  Joystick Collection, Report ID 1

       05 01        Usage Page (Generic Desktop)
       09 04        Usage (Joystick)
       A1 01        Collection (Application)
       09 01          Usage (Pointer)
       A1 00          Collection (Physical)
       85 01            Report ID (1)
       05 01            Usage Page (Generic Desktop)
       09 30            Usage (X)
       09 31            Usage (Y)
       16 50 FB         Logical Minimum (-1200)
       26 B0 04         Logical Maximum (1200)
       36 00 00         Physical Minimum (0)
       46 60 09         Physical Maximum (2400)
       75 0C            Report Size (12)
       95 02            Report Count (2)
       81 02            Input (Data,Var,Abs)
       C0             End Collection
       05 09          Usage Page (Button)
       19 01          Usage Minimum (Button 1)
       29 0E          Usage Maximum (Button 14)
       15 00          Logical Minimum (0)
       25 01          Logical Maximum (1)
       35 00          Physical Minimum (0)
       45 01          Physical Maximum (1)
       75 01          Report Size (1)
       95 0E          Report Count (14)
       81 02          Input (Data,Var,Abs)
       95 02          Report Count (2)
       75 01          Report Size (1)
       81 01          Input (Const)
       C0           End Collection

   Fourteen buttons is exactly the N64 button count: A, B, Z, Start, L, R,
   four C buttons and four D-pad directions. The mapping is CONFIRMED and is
   covered in ioctl-surface.txt section 7.

   The stick is reported as a 12-bit signed value in the range -1200 to
   +1200. The raw N64 stick is 8-bit signed and drv_BuildJoystickReport
   scales it: Y is negated to convert N64 up-positive into HID down-positive,
   both axes are multiplied by 16, optional corner stretch and range clipping
   applied, and the result is clamped to +/-1200. There is no dead zone. The
   scaling is detailed in ioctl-surface.txt section 7.1.

   Descriptor C at 00019c00 is byte-for-byte this joystick collection on
   its own. Descriptor B at 00019c40 is the mouse and keyboard
   collections without it.

5.  Report Layouts

   Every report carries a leading report ID byte, because the descriptor
   declares Report ID items.

   Input report 1, joystick, 6 bytes total:

       byte 0    report ID = 1
       byte 1    X bits 0..7
       byte 2    X bits 8..11 in the low nibble, Y bits 0..3 in the high
       byte 3    Y bits 4..11
       byte 4    buttons 1..8
       byte 5    buttons 9..14 in bits 0..5, bits 6..7 padding

   Input report 2, keyboard, 13 bytes total:

       byte 0      report ID = 2
       byte 1      modifier bits, LeftControl..RightGUI
       byte 2      reserved, constant
       byte 3..12  ten key usage slots, 0 = empty

   Output report 2, keyboard LEDs, 2 bytes total:

       byte 0    report ID = 2
       byte 1    bits 0..4 Num/Caps/Scroll/Compose/Kana, bits 5..7 pad

   Input report 3, mouse, 5 bytes total:

       byte 0    report ID = 3
       byte 1    bits 0..2 buttons 1..3, bits 3..7 padding
       byte 2    X, signed, -127..127, relative
       byte 3    Y, signed, -127..127, relative
       byte 4    Wheel, signed, -127..127, relative

   THE WHEEL BYTE CANNOT BE DRIVEN FROM A SCRIPT. drv_DispatchEvents calls
   drv_HidMouseMoveEvent with the wheel delta hard-wired to zero, and the
   _mouse_relative builtin carries only two arguments. The byte exists in the
   descriptor and in the report, and the driver keeps a running total for it
   at devext+0x1720, but nothing can ever write a non-zero value. See script-
   bytecode.txt section 7.2.

   WHICH REPORTS ARE LIVE IS CONFIGURABLE WITHOUT CHANGING THE DESCRIPTOR.
   drv_SubmitHidReport is the single exit for every report the driver
   produces, and it drops any report whose ID is not enabled in
   drv_VirtualDevicesMask, tested as 1 << (reportID - 1): bit 0 joystick, bit
   1 keyboard, bit 2 mouse. That mask comes from the VirtualDevices registry
   value read in drv_AddDevice - the same value that selects which of the
   three descriptors is reported in the first place. So the descriptor choice
   and the report gating are driven by one setting, and a replacement must
   apply both halves or it will publish collections it then refuses to feed.

   The 12-bit packing in report 1 is CONFIRMED. drv_BuildJoystickReport at
   00015150 writes exactly this layout, little-endian with no padding between
   the two fields:

       +0  X bits 0..7
       +1  X bits 8..11 low nibble, Y bits 0..3 high nibble
       +2  Y bits 4..11
       +3  buttons 1..8
       +4  buttons 9..16

   Reports 2 and 3 are confirmed too: drv_HidKeyEvent and
   drv_HidMouseButtonEvent assemble them byte for byte as described above,
   including the ten-slot key array and its ErrorRollOver overflow behaviour.
   See script-bytecode.txt section 7.

5.1.  How The Report State Is Kept

   The layouts above are what goes out. What decides WHEN, and what the
   bytes contain, is three small state machines - drv_HidKeyEvent
   (00014ad0), drv_HidMouseButtonEvent (00014c80) and drv_HidMouseMoveEvent
   (00014d10). A script never builds a report; its _key and _mouse_*
   builtins post events, and drv_DispatchEvents turns each one into a call
   to one of these.

   THE KEYBOARD. Three disjoint keycode ranges are accepted and everything
   else is ignored outright:

       0xE0..0xE7   modifiers, a bitmask, bit = keycode - 0xE0
       0x04..0xA4   ordinary keys, a dense array in press order
       0            release everything

   The array is kept DENSE AND ORDERED BY PRESS TIME: a press appends, and a
   release shifts the tail down over the gap rather than swapping the last
   entry into it. That ordering is not cosmetic - it is what makes the ten
   reported slots the ten OLDEST keys held rather than an arbitrary ten.

   THE ARRAY IS SIZED TO THE KEYCODE RANGE, NOT TO THE REPORT. devext
   reserves 0xA5 bytes at +0x1725 for 0xA1 possible keycodes, and a keycode
   already present is never appended twice, so the count cannot exceed the
   number of distinct accepted codes and the array cannot overflow. The
   sizing is deliberate, and a port that sizes the array to the ten report
   slots instead would be wrong.

   TEN-KEY ROLLOVER. Above ten keys held, all ten report slots are filled
   with 0x01 - HID ErrorRollOver - but the driver keeps tracking every key
   internally. Releasing back down to ten restores the real list without
   needing a fresh press.

   A REPORT GOES OUT ONLY ON A CHANGE. A press of a key already held, a
   release of one that is not, a modifier that is already set, or a
   release-everything when nothing is held all produce no report at all. The
   mouse BUTTON path tests the same way.

   THE MOUSE MOVEMENT PATH DOES NOT. drv_HidMouseMoveEvent has no change
   test and emits on every call, including one with all-zero deltas. It also
   accumulates running totals at devext+0x1718, +0x171C and +0x1720 which
   the report does not carry and which nothing in the driver ever reads
   back; the report carries the DELTAS.

5.2.  The Virtual Joystick Mode

   drv_SubmitJoystickReport (00014a00) is the joystick half, and it has a
   mode the other two do not.

   A submit with a NULL report means "send the last one again", and it is
   also the ONLY place the mode is re-evaluated:

       VirtualDeviceMode = ReportsEnabled ? 3 : 0

   so toggling the switch takes effect on the next idle resubmit rather than
   immediately. ReportsEnabled is a driver-wide global at 00019d70, written
   in exactly one place - drv_IoctlControlDevice - which makes it a
   control-device setting rather than a per-device one.

   With the mode non-zero the controller is bypassed entirely: a real report
   is DROPPED, and a NULL submit synthesises one instead from the device
   instance id at devext+0x3F8:

       byte 0    1
       byte 1    (InstanceId & 0x0F) << 4
       byte 2    InstanceId >> 4
       byte 3    0
       byte 4    0

   Read through the 12-bit packing in section 5, that is X = 1 and
   Y = InstanceId with no buttons - a fixed deflection, not a sweep.

   WHAT IT PARKS THE STICK AT IS THE ADAPTER'S IDENTITY. drv_AddDevice
   assigns that field as (counter % 1100) + 50, a per-adapter number in
   50..1149, and the range is chosen to be a legal stick coordinate. So
   virtual mode is not a fixed test pattern - it makes every adapter report
   a DIFFERENT, known stick position, which is how a user with several
   plugged in can tell which one is which. Control-device function 0x822
   resolves a device handle from the same number. An earlier revision of
   this note called the field VirtualStickValue and read it as a
   calibration constant; see driver-structures.txt.

6.  Device Identity

   From IOCTL_HID_GET_DEVICE_ATTRIBUTES:

       VendorID       0x06F7    Wish Technologies
       ProductID      0x0001
       VersionNumber  0x0100

   From IOCTL_HID_GET_STRING:

       manufacturer (index 0x0E)   L"Wish Technologies, Inc."
       product      (index 0x0F)   L"Adaptoid"
       serial       (index 0x10)   empty, Information = 0

   The HID descriptor returned by IOCTL_HID_GET_DEVICE_DESCRIPTOR
   declares bcdHID = 0x0001. That is an odd value; the conventional
   encoding for HID 1.0 is 0x0100. It is recorded here as observed.

7.  Minidriver IOCTL Surface

   drv_DispatchInternalDeviceControl at 000128d2 is installed into
   DriverObject->MajorFunction[0x0F]. hidclass.sys calls it; user mode
   never does. Codes are
   CTL_CODE(FILE_DEVICE_KEYBOARD, fn, METHOD_NEITHER, FILE_ANY_ACCESS),
   so code = 0x000b0000 | (fn << 2) | 3.

   +---------+----+-----------------------+---------------------------------+
   | Code    | fn | Name                  | Behaviour                       |
   +=========+====+=======================+=================================+
   | 0xb0003 |  0 | GET_DEVICE_DESCRIPTOR | builds 9-byte HID_DESCRIPTOR    |
   | 0xb0007 |  1 | GET_REPORT_DESCRIPTOR | copies the selected descriptor  |
   | 0xb000b |  2 | READ_REPORT           | drv_HidReadReport, guarded      |
   | 0xb000f |  3 | WRITE_REPORT          | accepted and discarded          |
   | 0xb0013 |  4 | GET_STRING            | manufacturer/product/serial     |
   | 0xb001f |  7 | ACTIVATE_DEVICE       | devext[0x328 + i] = 1, i < 3    |
   | 0xb0023 |  8 | DEACTIVATE_DEVICE     | devext[0x328 + i] = 0, i < 3    |
   | 0xb0027 |  9 | GET_DEVICE_ATTRIBUTES | VID/PID/version, 0x20 bytes     |
   | other   |  - | unsupported           | STATUS_NOT_SUPPORTED            |
   +---------+----+-----------------------+---------------------------------+

   A guard runs before the switch: drv_IsDeviceReady(devext) returning zero
   completes the IRP with STATUS_DEVICE_NOT_CONNECTED (0xC0000056).

   WRITE_REPORT returning success without doing anything is worth
   noting. The keyboard LED output report is therefore accepted and
   dropped rather than acted on, which matches the hardware: there are
   no LEDs on an N64 controller.

   The three activate/deactivate slots at devext+0x328 correspond to the
   three top-level collections. INFERENCE: the index order has not been
   confirmed against the descriptor.

8.  The Controller Poll

   drv_BuildJoystickReport at 00015150 turns a raw 5-byte controller poll
   into HID report 1. The raw layout is X, Y, a status byte, then the two
   button bytes.

8.1.  The Polling Engine

   Controller state arrives as a continuous double-buffered USB interrupt
   read. Two IRPs are kept in flight at all times, so one read is always
   outstanding while the other is being processed. There is no timer in this
   path.

   Two slots of 0x14 bytes are based at devext+0x2f4:

       slot n at devext + n * 0x14
         +0x2f0  cancel-in-progress latch
         +0x2f4  the IRP
         +0x2f8  the URB
         +0x2fc  5-byte data buffer
         +0x301  slot active flag

       devext+0x318  stop-reason bitmask; polling runs only while it is 0
       devext+0x320  restart pending flag
       devext+0x324  work item used to restart after an error

   drv_PollStart at 00016a70 clears one bit from the stop mask and, once no
   reasons remain, marks both slots active and submits both IRPs.

   drv_PollSubmit at 00016940 builds each read as a 0x48-byte URB, exactly
   sizeof(_URB_BULK_OR_INTERRUPT_TRANSFER), with function 0x09
   (URB_FUNCTION_BULK_OR_INTERRUPT_TRANSFER):

       PipeHandle            from devext+0x290 +0x18
       TransferBufferLength  5
       TransferFlags         3   IN | SHORT_TRANSFER_OK
       TransferBuffer        the slot's own buffer at +0x2fc

   It is sent down as IOCTL_INTERNAL_USB_SUBMIT_URB (0x220003) with
   drv_PollComplete as the completion routine. Five bytes is the entire
   controller state and matches the raw layout in section 8 exactly.

   drv_PollComplete at 00016c47 validates three things before accepting a
   packet: IoStatus.Status is zero, the URB status is not negative, and
   URB->TransferBufferLength is exactly 5. Anything else counts as an error.
   On success it calls drv_BuildJoystickReport with the slot buffer and
   immediately resubmits that slot.

   drv_PollStop at 00016b00 ORs a reason into the stop mask, cancels
   whichever IRPs are outstanding with IoCancelIrp, and frees them.

   ERROR RECOVERY. A failed read queues the work item at devext+0x324, whose
   routine is drv_PollRestartWorker at 00016da7. That worker tries up to
   THREE times to recover the port and restart polling. If all three fail it
   cycles the port, which forces the device to re-enumerate.

   THE SENTINEL 0xC0012345 IS drv_RecoverPort SAYING IT ALREADY GAVE UP.
   Earlier revisions of this note recorded its meaning as unestablished. It
   is not an NTSTATUS at all: drv_RecoverPort resets the port only when the
   device is still connected but the port has been disabled, and in every
   other case cycles the port ITSELF and returns that value. The worker tests
   for it and stops - both the retry and its own cycle are skipped, because
   repeating either would cycle the port over and over.

   RESOLVED: the string "PolRst" at 00016c40, referenced from inside
   drv_PollComplete, is NOT a work item name or a debug tag. It is the Tag
   argument to the hand-rolled remove lock - drv_PollComplete calls
   drv_LockAcquire(&RemoveLockB, 0x16c40) and drv_PollRestartWorker the
   matching release with 0x16da0, which is the identical six-character
   string. The pair is what keeps the device alive across the queued work.

8.2.  The Status Byte

   The whole function is gated on status & 0xFC == 0x80, so bit 7 is a
   validity marker and bits 6 through 2 must be clear. Only the low two bits
   carry data, and they follow the N64 controller status convention:

       bit 0   accessory (Pak) currently present
       bit 1   accessory removed since the last status query

   The previous value is kept at devext+0x16F5 so transitions can be
   detected. When bit 1 falls from 1 to 0, devext+0x3E4 is reset to 0, which
   sends the accessory probe state machine back to the start: 0 means probe
   needed, 1 means probing, 2 or more means ready. IOCTL fn 0x836 selector 4
   reads that state. When bit 0 changes, FUN_00013D00 queues a work item with
   0x34 for inserted and 0x35 for removed.

8.3.  On-Controller Tuning Mode

   The driver implements a live adjustment mode entered from the controller
   itself, with no user-mode involvement. The entry test is L + R + Z held
   together with Start. Pressing L + R + Start also makes the controller
   assert its own Reset bit, which the code accepts as an alternative to
   Start.

   While the mode is active the stick and D-pad act as controls:

       stick X   devext+0x15E0 = 1e9 / (2400000 / v)^2, where v is the
                 clamped X plus 1200, giving 0..2400. About 250 at
                 centre and 1000 at full right. Below 76, v gives 0.
       stick Y   devext+0x15DC = (clamped Y + 1200) / 24, giving 0..100
                 devext+0x15D8 = 100 minus that
       D-pad     devext+0x15E8 from a fixed set:
                     D-down              -> 0
                     D-down + left/right -> 12
                     D-left or D-right   -> 25
                     D-up + left/right   -> 50
                     D-up                -> 100

   THE Y USED HERE IS THE NEGATED ONE, which is easy to miss because the
   negation is not part of the tuning code. The stick path earlier in the same
   function overwrites its Y local with the HID-convention negated value, and
   the tuning block further down reads that local. So pushing the stick UP
   drives the duty cycle DOWN. Confirmed by emulation: full up gives duty 0
   and complement 100, full down gives 100 and 0.

   EXIT IS TWO-STAGE, and the D-pad is deliberately excluded from it so that
   holding a direction keeps you in the mode:

       releasing the shoulder and face buttons clears bit 1 of
       devext+0x15E4, leaving 1 - still ACTIVE and still tracking the stick;

       pressing any of those buttons again from that state zeroes it and
       calls drv_EffectKick, committing the values.

   So the mode is NOT left by releasing the combination. It is left by the
   next button press after releasing it. An earlier revision of this section
   said the next poll alone would zero it, which is wrong: with everything
   released, every later poll takes the same branch and the mode stays at 1.
   Verified by emulation.

   WHAT THE MODE DOES TO THE ENGINE. Both branches sit inside
   drv_EffectEvaluate and both bypass the effect set entirely:

       intensity  replaced by (TuneDuty * TunePeriod + 999) / 1000
       pulses     driven by a 12-slot counter instead of the modulator,
                  forcing a pulse for the first N slots of every twelve,
                  N = (TuneDutyComplement * TunePeriod + 8000) / 11112 + 1

   So while tuning, the motor runs from the calibration alone and gives a
   steady periodic buzz rather than the dithered pattern the modulator
   produces - something to calibrate against.

   devext+0x15E8 then gates a scan of the 32 effect slots for one whose
   header field equals 0x40 and which is running.

   INFERENCE: a period, a duty cycle and a strength preset, committed to the
   effect engine on release, reads as live tuning of a Rumble Pak feedback
   effect from the controller. Not established. See ioctl-surface.txt section
   5.

9.  Consequences For The Replacement Driver
   The descriptor in section 4 is the contract. A replacement that
   reproduces it byte-for-byte will be indistinguishable to every
   application, which is the stated goal of this project.

   Points that carry over unchanged:

   -  The three collections and their report IDs. Report IDs 1, 2 and 3
      are baked into anything already configured.
   -  VID 0x06F7 / PID 0x0001, if existing configuration tooling is to
      keep working.
   -  The 10-slot key array, not the usual 6.

   Points that do not carry over:

   -  The registry path is under Software\Wish Technologies\Adaptoid
      with no WOW64 redirection considered. On 64-bit Windows a
      kernel-mode RtlQueryRegistryValues against \REGISTRY\Machine\
      Software resolves to the 64-bit view, so a 32-bit configurator
      writing the same path lands in Wow6432Node and the driver will not
      see it. This must be handled explicitly in any port.
   -  The descriptor selection table stores raw 32-bit pointers. On x64
      these become 64-bit, so the 8-byte entry stride changes.
   -  Selecting the personality by a registry DWORD read once at
      AddDevice is workable but coarse. It is recorded here as the
      original behaviour, not as a recommendation.
