Adaptoid Reverse Engineering                                 Design Note


                  REPLACEMENT ARCHITECTURE


Abstract

   The reverse engineering notes in this directory describe what the 2001
   driver does. This note is different in kind: it records the design
   decisions for the replacement, and the reasoning behind them, before
   any code is written.

   The central finding is that the property worth preserving is narrower
   than it first appears, and it can be had without reproducing the
   original architecture at all.

   Statements about Windows behaviour here are design reasoning, not
   reverse engineering. Where something was verified against the
   binaries, the relevant note is cited.

1.  The Property Worth Preserving

   The Adaptoid's distinguishing feature is not that it remaps buttons.
   Plenty of software does that. It is that the remapped output is
   indistinguishable from real hardware to every application, including
   ones that ignore injected input.

   User-mode remappers call SendInput or post messages. Games that read
   through DirectInput, RawInput or a polling loop on GetAsyncKeyState
   frequently do not see that input at all. The Adaptoid does, because
   its keystrokes arrive through kbdclass exactly as a real keyboard's
   would.

   THAT is the property to preserve. Everything else - the scripting
   language, the effect engine, the Controller Pak access - is valuable
   but secondary, and none of it depends on the driver architecture.

2.  How The Original Achieves It

   wishk201.sys is the FUNCTION DRIVER for the device. wishna1.inf
   matches the hardware ID USB\VID_06F7&PID_0001, and a hardware-ID match
   outranks the generic HID compatible-ID match that would otherwise load
   the inbox hidusb path. So PnP loads this driver instead of the inbox
   one. The configurator also references \inf\input.inf, consistent with
   it displacing that install.

   drv_DriverEntry then calls HidRegisterMinidriver, which stacks
   hidclass.sys above it. From there:

       1. hidclass requests a report descriptor
          (IOCTL_HID_GET_REPORT_DESCRIPTOR)
       2. the minidriver returns its OWN composite descriptor - mouse,
          keyboard and joystick, see hid-descriptor.txt section 4
       3. hidclass creates one child PDO per top-level collection
       4. kbdhid and kbdclass attach to the keyboard PDO, mouhid and
          mouclass to the mouse PDO

   Meanwhile the driver reads 5-byte raw packets off the interrupt pipe
   and SYNTHESISES new HID reports from them; see hid-descriptor.txt
   section 8.1 for the polling engine and script-bytecode.txt section 7
   for the report builders.

   The device's own HID personality - the one that makes the adapter work
   driverless on a modern machine - is simply not used. It is replaced.

3.  Why It Is Not A Filter Driver

   It is tempting to describe the driver as intercepting the controller's
   USB data and rewriting it. That is a reasonable guess and it is wrong.

   There is nothing above it to intercept and nothing below it producing
   HID data. It owns the device, speaks the adapter's vendor protocol
   directly (usb-transport.txt), and manufactures HID reports that have
   no relationship to what the hardware would have reported on its own.

   The wrapper layer documented in ioctl-surface.txt section 1 IS an
   interception, but of a different thing entirely: it multiplexes the
   driver's private configuration API onto the same dispatch table that
   hidclass owns. It has nothing to do with input.

   To be fair to the intuition, there are two layers here and the answer
   differs by layer. In the DATA FLOW sense it is reasonable to call the
   driver a pass-through: raw USB packets arrive from the bus driver below,
   the driver transforms them, and HID reports go up to the OS. Data really
   does flow through it and get changed on the way.

   In the WINDOWS ARCHITECTURE sense it is not a filter, and the difference
   is load-bearing. A filter attaches to a stack that ALREADY has a function
   driver and watches IRPs go past; it coexists with the original and must
   not break it. This driver IS the function driver. Nothing else is on that
   stack. Remove it and hidusb loads instead and behaves completely
   differently.

   The consequence that matters: because it REPLACES hidusb, the device's own
   HID personality never reaches the OS at all. That is exactly the double
   visibility problem architecture 3 has and this one does not; see section
   7.1.

4.  Why The Existing Virtual Pad Drivers Do Not Solve This

   The obvious modern shortcut is an existing virtual controller driver.
   It does not work, for a structural reason.

   vJoy creates a virtual DirectInput JOYSTICK. ViGEmBus emulates an Xbox
   360 pad over XUSB, which is not even HID, or a DualShock 4. Both are
   gamepad emulators by design. Neither emits keyboard or mouse reports.

   The "keyboard and mouse support" visible in those ecosystems runs the
   other way: mapping a real keyboard and mouse as an input SOURCE onto a
   virtual gamepad, for playing controller-only games with mouse and
   keyboard. That is the reverse of what is needed here.

   The missing capability is precisely the one the Adaptoid has: a single
   virtual device declaring MULTIPLE top-level collections, so that
   keyboard, mouse and gamepad input can all originate from it.

5.  Candidate Architectures

   +---+--------------------------+----------+------------+-------------+
   | # | Approach                 | Generic? | Runtime    | Signing     |
   |   |                          |          | attach     | burden      |
   +===+==========================+==========+============+=============+
   | 1 | Per-device HID           | no       | no         | full driver |
   |   | minidriver, as 2001      |          |            |             |
   | 2 | Lower filter on the      | partly   | with a     | full driver |
   |   | USB stack                |          | device     |             |
   |   |                          |          | restart    |             |
   | 3 | Virtual composite HID    | yes      | yes        | two drivers,|
   |   | device plus a user-mode  |          |            | logic       |
   |   | mapper                   |          |            | unsigned    |
   +---+--------------------------+----------+------------+-------------+

   5.1.  Per-device minidriver

   Reproduce the original: own the device, speak its protocol, present a
   composite descriptor. It must be written per controller, needs an INF per
   hardware ID, and the mapping engine lives in kernel mode where every bug
   is a bugcheck.

   Those costs are real but they are costs of SCALE, not of correctness. For
   a single known controller this is the better design, because it is a
   replacement rather than an addition and therefore has none of the problems
   in section 7. Section 8 works the case through end to end.

   5.2.  Lower filter on the USB stack

   Sit below hidusb, rewrite the GET_DESCRIPTOR(Report) response to
   advertise extra collections, and rewrite the interrupt-in data. This
   is the architecture most people imagine, and it is buildable.

   The costs are real: HID report descriptors must be parsed and rebuilt
   per device, and the descriptor is consumed when hidclass starts the
   device, so changing it requires restarting that device rather than
   flipping a flag.

   5.3.  Virtual composite HID device

   Leave the real controller entirely alone. Create a software-only HID
   device that declares keyboard, mouse and gamepad collections, and feed
   it reports from a user-mode service that reads the real controller and
   runs the mapping.

   Because the virtual device is a genuine HID device, its reports travel
   the same kbdclass and mouclass path as real hardware. The property
   from section 1 is preserved in full, even though the mapping logic
   runs in user mode.

   That is the key realisation: the guarantee comes from the OUTPUT path,
   not from where the logic runs. The original put the logic in the
   kernel because in 2001 there was no supported way to create a virtual
   HID device, not because the kernel was required.

   This approach is ADDITIVE rather than a replacement, and that has a
   significant cost which section 7 sets out in full. Do not read this
   subsection on its own.

6.  Recommended Design

   NOTE BEFORE READING: this section recommends architecture 3 for the
   GENERAL case of supporting arbitrary controllers, and that reasoning
   stands. THIS PROJECT went the other way and chose architecture 1,
   because it targets one known adapter; see section 8.5 for the
   comparison and section 11 for the decision.

   Architecture 3, built on the Virtual HID Framework.

   VHF is the supported Windows mechanism for a driver to create a HID
   device with no hardware behind it. VHF_CONFIG takes a pointer to a raw
   HID report descriptor and its length, so an arbitrary descriptor -
   including a multi-collection one - can be supplied verbatim.
   VhfReadReportSubmit pushes input reports up.

   In outline:

       kernel   a small VHF-based driver whose only job is to create the
                virtual device from a descriptor handed to it, and to
                pass input reports through

       user     a service that
                  - enumerates real controllers
                  - reads the chosen one (HID or RawInput for HID pads,
                    XInput for Xbox-family pads, which are not HID)
                  - runs the mapping and scripting
                  - submits reports to the virtual device

       required a device-hiding filter so applications do not also see
                the original controller; see section 7, this is NOT
                optional in practice

   The descriptor from hid-descriptor.txt section 4 can be used
   unchanged. Doing so has a specific benefit beyond convenience: report
   IDs 1, 2 and 3 and the button numbering stay identical, so profiles
   and muscle memory built on the original still behave the same way.

   Kernel code is then small, generic and stable. It contains no device
   protocol, no scripting, no timing. Only the virtual device driver
   needs signing; the mapping engine, including a port of the flex and
   bison front end, is an ordinary user-mode program that can be
   developed and debugged normally.

   6.1.  Where the original's timing guarantees go

   The original runs scripts in kernel mode on a timer, with a
   100000-instruction budget per quantum; see script-bytecode.txt
   section 6.1. A user-mode service can be descheduled, so its timing is
   less deterministic.

   In practice this matters far less than it sounds: the script time base
   is 1/64 second, which a normal thread meets comfortably. If a specific
   effect turns out to need tighter timing, that piece alone can be moved
   into the driver later without disturbing the architecture.

7.  The Cost Of The Recommended Design

   Architecture 3 has one structural weakness that the original does not, and
   it is worth stating plainly rather than burying in a trade-off table.

7.1.  It Is Additive, Not A Replacement

   The original REPLACES the device's HID personality. The adapter's own
   descriptor is never used, so exactly one device exists in the system and
   it is the composite one.

   A virtual HID device ADDS. The real controller continues to enumerate
   normally as whatever it already was, and the virtual device appears
   alongside it. Both react to the same physical button press:

       controller --USB--> hidclass --> gamepad PDO --> applications
                                        |
                                        v
                                 user-mode service
                                        |
                                   mapping engine
                                        v
                                  VHF virtual device
                                        |
                              kbdclass / mouclass / gamepad

   It is a tap rather than a splitter, and the path leaves the kernel and
   comes back.

7.2.  Why Double Visibility Is Worse Than Clutter

   Suppose A is mapped to the W key. An application reading the keyboard sees
   W, which is correct. But the same application also sees gamepad button 1
   go down, because the real controller is still there.

   Many games switch to controller mode the moment they detect a gamepad:
   button glyphs replace key prompts, aim assist and deadzone handling
   change, and some ignore keyboard input entirely while a pad is present. So
   the failure is not cosmetic. It can make the remapping useless in exactly
   the titles it was meant for.

   This is the single largest cost of architecture 3, and the original design
   does not have it.

7.3.  Mitigation, And Its Price

   The fix is a device-hiding filter: a lower filter that makes the source
   controller invisible to every process except an allow-listed one, so
   applications see only the virtual device. With that in place the
   observable behaviour matches the original.

   The price is honesty about the component count. The design needs TWO
   kernel components, not one: the VHF driver and the hiding filter. Both are
   still generic and device-independent, and the hiding filter is simple
   because it performs no descriptor surgery - it only makes a devnode
   invisible - but the claim of a single small driver was too optimistic.

   A partial cosmetic improvement is available regardless: VHF_CONFIG accepts
   a ContainerID. Setting it to the real controller's makes Windows group the
   two as one physical device in the user interface. That does not stop an
   application enumerating both, but it avoids presenting the user with two
   unrelated devices.

7.4.  Other Costs

   LATENCY. The path is USB, then hidclass, then a user-mode read, the
   mapping, then back into the kernel through VHF and out via kbdclass. Two
   boundary crossings plus thread scheduling, against the original doing the
   whole thing inside a completion routine. Typically a millisecond or two:
   irrelevant for most use, measurable for frame-accurate input.

   LIFETIME. If the mapping service crashes, is terminated, or has not
   started yet, remapping simply stops. The original cannot fail that way
   because there is no separate process to fail. The virtual device's reports
   DO reach the logon screen and the secure desktop, since they are genuine
   HID input, but only while something is feeding it - which means the mapper
   must run as a system service rather than a tray application. That is a
   design requirement, not a detail.

   ANTI-CHEAT. Some titles flag recognised virtual input drivers. A driver
   presenting itself as real hardware, as the original does, attracts less
   attention than a well-known virtual bus.

   RE-BIND. The real controller can come and go across sleep, resume and
   replug while the virtual device persists. The service has to notice and
   re-attach, which the original got for free from PnP.

7.5.  When To Prefer Another Architecture

   If the replacement is only ever going to target the Adaptoid itself, then
   architecture 1 - a per-device minidriver, as the original does - avoids
   every problem in this section. It is more kernel code and it is device-
   specific, but it is a replacement rather than an addition, and the double-
   visibility question never arises.

   Architecture 3 earns its complexity only if supporting arbitrary
   controllers is actually a goal. That is a decision to make deliberately
   before writing code, not after. Section 8 works the single-device case
   through end to end, including the comparison that decides it.

8.  Worked Example: Owning A Third-Party HID Gamepad

   Premise: a generic PlayStation-to-USB adapter, of the kind that needs no
   driver because its firmware presents a standard HID gamepad. The goal is
   Adaptoid-style behaviour - scripting and remapping to keyboard and mouse -
   for that one device.

   This is architecture 1 applied to somebody else's hardware, and for a
   single known target it is the right choice.

8.1.  What Sits Below You

   The common misconception is that such a driver receives HID reports from a
   lower HID driver and edits them. It does not. There is no HID layer
   beneath it:

       kbdclass / mouclass / gamepad     per-collection PDOs
       hidclass.sys                      linked into the same FDO
       YOUR DRIVER                       the function driver, the FDO
       ============ IRP / URB boundary ============
       USB PDO (usbhub)
       usbport / usbehci / usbxhci

   You submit URBs to the USB BUS DRIVER and receive raw endpoint bytes. For
   a HID gamepad those bytes happen to be the HID input report its own
   descriptor defines, but nothing forces you to treat them as HID. They are
   just bytes, and you decide what they mean.

8.2.  Bring-Up, Step By Step

   Every step below already has a worked reference in these notes, because
   the Adaptoid driver does the same things.

       1  INF matches USB\VID_xxxx&PID_yyyy. A hardware-ID match
          outranks the compatible-ID match (USB\Class_03) that would
          otherwise load hidusb. This is how vendor peripheral drivers
          routinely take over HID devices.

       2  DriverEntry calls HidRegisterMinidriver so hidclass stacks on
          top. See driver-lifecycle.txt section 1.

       3  On IRP_MN_START_DEVICE, fetch the device and configuration
          descriptors, issue SELECT_CONFIGURATION, and keep the
          interrupt IN pipe handle. See driver-lifecycle.txt section
          3.1; note the Adaptoid blindly takes Pipes[0], which you
          should not copy.

       4  Poll with a double-buffered pair of interrupt URBs so one read
          is always outstanding. See hid-descriptor.txt section 8.1.

       5  Parse the raw bytes into your own state.

       6  Synthesise composite reports and submit them. See
          script-bytecode.txt section 7 for the report builders.

       7  Serve your own descriptor on
          IOCTL_HID_GET_REPORT_DESCRIPTOR. The Adaptoid's 185-byte
          descriptor can be reused verbatim; see hid-descriptor.txt
          section 4.

8.3.  The One Thing The Reverse Engineering Cannot Give You

   The adapter's input report byte layout. Establish it BEFORE writing the
   driver, while the device is still an ordinary HID device:

       - dump its report descriptor through HidD_GetPreparsedData and the
         HID parser API, or capture enumeration with a USB analyser
       - log its input reports while pressing each button and sweeping
         each stick

   That gives you the byte and bit position of every control. Check
   specifically whether the device uses REPORT IDs: if it does, byte 0 of
   what you read is the report ID and the payload begins at byte 1; if not,
   the payload begins at byte 0. Its own descriptor answers this.

8.4.  Gotchas

   SIGNING. Windows 10 and 11 on x64 will not load an unsigned driver.
   Attestation signing through Partner Center covers a non-WHQL driver. For
   personal use, test-signing mode works but weakens other protections.

   MULTI-PORT ADAPTERS. Many of these expose two controllers, sometimes as
   two HID collections and sometimes as one collection with a port byte.
   Determine which before designing your descriptor, because it changes how
   many top-level collections you declare.

   MULTIPLE INTERFACES. Cheap adapters occasionally expose more than one USB
   interface. Pick the right one deliberately rather than copying the
   Adaptoid's assumption that the first pipe is the one you want.

   YOU INHERIT EVERYTHING. Owning the device makes you responsible for PnP,
   power, surprise removal and selective suspend. driver-lifecycle.txt is a
   working template for all of it, including the teardown ordering in section
   3.2 that keeps you from touching USB resources the bus driver has already
   reclaimed.

8.5.  Which Way To Go

   +-------------------+----------------------+------------------------+
   | Concern           | Own the device       | VHF plus hiding filter |
   +===================+======================+========================+
   | Double visibility | none by construction | needs a hiding filter  |
   | Per new device    | new INF and protocol | nothing                |
   |                   | work                 |                        |
   | Mapping logic     | kernel mode          | user mode              |
   | Kernel components | one                  | two                    |
   | Debugging         | bugchecks            | ordinary debugger      |
   +-------------------+----------------------+------------------------+

   For ONE known adapter, owning it is simpler and strictly better. For "any
   controller the user plugs in", architecture 3 wins despite section 7. The
   deciding question is how many devices are actually intended to be
   supported, and it is worth answering before code is written rather than
   during.

9.  Runtime Attach And Device Restart
   The question "can it attach to an arbitrary controller at runtime
   without a reboot" has a different answer per architecture.

   Architecture 3 - YES, fully dynamic. Nothing touches the source
   device's driver stack. The service enumerates controllers, the user
   picks one, and mapping starts. Plugging in a different pad is picked
   up immediately. No INF per device, no device restart, no reboot.

   Architecture 2 - possible but awkward. One CLASS-WIDE filter can be
   installed once, with a user-mode app telling it which VID and PID to
   act on, which avoids an INF per device. But since the advertised
   report descriptor changes, the target device must be restarted for
   hidclass to re-read it. That can be triggered programmatically, so the
   user sees a brief disconnect rather than a reboot.

   Architecture 1 - NO. A new device means a new INF and a driver
   install.

   Note for Xbox-family controllers specifically: the original Xbox, 360
   and One pads use XUSB rather than HID, so no HID filter will see them.
   Under architecture 3 they are simply read through XInput instead,
   which is a detail of the user-mode service rather than a structural
   problem. Generic PlayStation-style USB adapters are ordinary HID
   gamepads and need no special handling.

10. What Carries Over From The Reverse Engineering
   Under architecture 3, much of the original becomes reference rather
   than specification. What still matters:

   -  The HID report descriptor and the three report layouts, which
      should be reproduced exactly. See hid-descriptor.txt.

   -  The bytecode instruction set and the native builtin library, if
      existing compiled scripts are to keep working. See
      script-bytecode.txt sections 6 and 7. The interpreter moves to
      user mode but the semantics do not change.

   -  The button map, because it defines which N64 button becomes which
      HID button. See ioctl-surface.txt section 7.

   -  The three defects in known-defects.txt, each of which is a
      deliberate decision rather than an automatic fix. The stick
      corner stretch in particular shaped how the original felt.

   What does NOT carry over: the USB vendor protocol, the accessory
   probe, the polling engine, the PnP and power paths, and the whole
   private IOCTL surface. Those exist to talk to Adaptoid hardware, and
   under architecture 3 the inbox HID driver does that job.

   The one case where they DO still matter is Adaptoid-specific
   functionality that no generic path provides: Controller Pak read and
   write, and Rumble Pak feedback. Those need the vendor protocol in
   usb-transport.txt, and therefore a device-specific component. Treat
   them as an optional add-on to the generic design, not as part of it.

11. Open Decisions
   -  RESOLVED: ARCHITECTURE 1. The replacement is a per-device HID
      minidriver that owns the adapter, not the virtual-HID design of
      section 6. The deciding question was the one section 8.5 poses -
      how many devices are actually intended to be supported - and the
      answer is one, the Adaptoid itself. For a single known adapter,
      owning the device avoids every cost in section 7, above all the
      double-visibility problem, and needs one kernel component rather
      than two. Section 6 remains the right recommendation for the
      general case and should be read that way.

      The source tree is ../src_drv; see src_drv/README.txt. It builds
      wishk300.sys and a user-mode harness, wishk300.exe, from the same
      C source.

   -  Whether to support the original compiled bytecode at all, or to
      keep only the source language and recompile. Supporting the
      bytecode preserves existing profiles; dropping it removes the need
      to reimplement the interpreter exactly.

   -  RESOLVED, and it was never a defect. The stick cross-coupling is
      the vendor's documented octagonal-to-square corner stretch; see
      known-defects.txt section 3. A replacement should implement it and
      expose both it and the range clipping as tunables. Whether to make
      it a user-visible option or apply it silently is still open.

   -  Whether the Adaptoid-specific add-on is worth building at all, or
      whether Controller Pak access and rumble are better left to the
      original hardware on an original machine.

   -  ARCHITECTURE 3 ONLY, and therefore moot under the decision above:
      whether to hide the source controller from applications by
      default. Hiding avoids doubled input but surprises users who
      expect the pad to still work normally in other software.
      Architecture 1 replaces the device, so nothing is doubled.
