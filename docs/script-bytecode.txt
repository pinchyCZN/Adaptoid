Adaptoid Reverse Engineering                                 Analysis Note
wishd201.exe                                                 2001 config tool


                  SCRIPT COMPILER AND BYTECODE


Abstract

   The Adaptoid button scripting language is compiled, not interpreted in
   user mode. wishd201.exe contains a flex scanner and a bison parser that
   translate a C-like source script into a stream of 32-bit opcodes, which is
   then downloaded into wishk201.sys and executed in kernel mode.

   That is why a script such as "A repeats as mouse clicks" reaches every
   application as genuine HID input: no part of the translation happens above
   the driver.

   This note records the location of the compiler, the compile pipeline, the
   download buffer format, the instruction encoding, the complete opcode set
   and the native builtin library.

   The opcode set was recovered from the compiler and then confirmed
   instruction by instruction against the driver-side interpreter, so the
   semantics in section 6 are read out of executing code rather than deduced
   from code generation.

   Everything here is read out of the Ghidra database for wishd201.exe, with
   driver-side cross-checks against wishk201.sys. Statements not directly
   supported by an instruction or a byte are marked INFERENCE.

1.  Evidence That It Is Flex And Bison

   The original developer stated that the scripting language was built with
   flex and bison. The binary confirms it.

   Flex runtime strings, all referenced from cfg_yylex at 0040aa80:

       00421174  "fatal flex scanner internal error--no action found"
       004211a8  "input in flex scanner failed"
       004211c8  "fatal error - scanner input buffer overflow"
       004211f4  "fatal flex scanner internal error--end of buffer missed"
       0042122c  "out of dynamic memory in yy_create_buffer()"
       0042125c  "flex scanner push-back overflow"

   Bison runtime strings, referenced from cfg_yyparse at 00409950:

       004210a8  "parse error"
       0042115c  "parser stack overflow"

   "parse error" rather than "syntax error" places this at bison 1.x, which
   is consistent with a tool built in or before 2001. A large character table
   sits at 0041f4da. INFERENCE: this is the scanner equivalence-class array
   that flex emits as a 256-entry map from character to class.

   | cfg_CompileScript          | 0040bc00 | compile one script, top level        |
   | cfg_EmitWord               | 0040cb00 | append one 32-bit word               |
   | cfg_EmitOpOperand          | 0040cb90 | append opcode word plus operand word |
   | cfg_ConcatCode             | 0040cbf0 | concatenate two code lists           |
   | cfg_CodeLength             | 0040ca20 | length of a code list in words       |
   | cfg_CurrentPc              | 0040caa0 | current code length, used as PC      |
   | cfg_EmitSymbolRef          | 0040c9b0 | load a global or a local             |
   | cfg_EmitStoreToSymbol      | 0040c480 | emit a store to a named symbol       |
   | cfg_EmitLoop               | 0040c800 | build for/while/do from fragments    |

   | cfg_DownloadScript         | 00404700 | DeviceIoControl 0xb98c20f0           |

   Scripts are held per button. The UI walker at 00408af0 iterates 16 entries
   of 0x43C bytes each from 00425788 to 00429b48, which matches the 16
   entries of drv_ButtonMap in the driver: one script slot per bit position
   in the N64 button word.

3.  The Compile Pipeline

   cfg_CompileScript performs:

       cfg_PredeclareSymbols()        reset code generator state
       cfg_ScriptCompile(text)    point the lexer at the source string
       cfg_yyparse()         parse; grammar actions emit into DAT_0045b5b4

   The global DAT_0045b5b8 holds the result: zero on success, non-zero is the
   error code returned to the caller. On failure the caller receives line and
   column information from DAT_0045b5d8, DAT_0045b5c0, DAT_0045b5e0 and
   DAT_0045b5c8, and the message text is copied out of DAT_0045b560. The UI
   surfaces this as "Script compilation error" at 0041f288.

   On success a fixed epilogue and prologue are wrapped around the body:

       cfg_EmitOpOperand(tail, 0x110, sym[5] | 0x20000000)
       cfg_EmitOpOperand(tail, 0x020, 0x80)
       cfg_EmitWord     (tail, 0x082)
       cfg_EmitOpOperand(NULL, 0x170, cfg_CodeLength(body))
       cfg_ConcatCode(prologue, body)
       cfg_ConcatCode(prologue, tail)

   The symbol used in the first epilogue instruction comes from cfg_ScriptEmit
   looking up the name at 004212a0, and its field [5] is or-ed with
   0x20000000 before being used as the operand. INFERENCE: 0x20000000 is a
   global-storage tag rather than part of the value, since cfg_EmitSymbolRef
   applies the same bit only on the global branch.

4.  Download Buffer Format

   The packed buffer is:

       +0x00  dword         opcode count
       +0x04  dword         flags/metadata, from DAT_0045b608
       +0x08  dword[count]  the opcode stream

   cfg_DownloadScript sends it with

       DeviceIoControl(h, 0xb98c20f0, buf, buf[0] * 4 + 8, &out, 4, ...)

   which matches the driver length check exactly: wishk201.sys requires the
   input length to equal *input * 4 + 8. See ioctl-surface.txt section 5a for
   the driver side. A count of zero unloads the script.

   INFERENCE: the count is masked with 0x3FFFFFFF in the copy loops of both
   cfg_CompileScript and cfg_EmitWord, so the top two bits of that dword may
   be flags rather than count. Not established.

5.  Instruction Encoding

   The code list used during compilation has the layout

       +0x00  dword    words used
       +0x04  dword    capacity in words
       +0x08  dword[]  the words

   It doubles in capacity when full, starting at 8 words. An instruction is
   one 32-bit opcode word, optionally followed by one 32-bit operand word.
   Two bits of the opcode are structural:

   +-------+-----------------------------------------------------+
   | Bit   | Meaning                                             |
   +=======+=====================================================+
   | 0x100 | The opcode is followed by an operand word.          |
   | 0x400 | The operand is an unresolved PC-relative reference. |
   +-------+-----------------------------------------------------+

   Bit 0x100 is the decoder stride rule, and it is not a guess. The
   instruction walker inside cfg_CloseScopeAndBackpatch advances an extra
   slot exactly when (opcode & 0x100) is non-zero. It holds for every opcode
   recovered: 0x110, 0x170, 0x172, 0x190, 0x9f0, 0x9f1, 0xd91 and 0xd92 carry
   operands, and none of the others do.

   Bit 0x400 is set by cfg_EmitOpOperand, which rewrites the operand as

       operand = ((short)(operand >> 16) << 16)
               | ((operand - cfg_CurrentPc(list)) & 0xFFFF)

   so the low half becomes a signed word displacement from the emit point and
   the high half is preserved as a scope identifier. When the owning scope
   closes, cfg_CloseScopeAndBackpatch matches the high half against the scope
   being closed, clears bits 0x0C00, and sign-extends the operand to a final
   32-bit displacement.

   Note that cfg_EmitOpOperand is really just "emit two words". It is
   sometimes used to emit two independent no-operand opcodes in one call:
   cfg_EmitOpOperand(list, 0x20, 0x80) in cfg_CompileScript produces the same
   two words as the separate cfg_EmitWord(0x20) and cfg_EmitWord(0x80) calls
   in grammar action 7.

6.  Opcodes

   The opcode set was first recovered from the compiler by enumerating every
   caller of cfg_EmitWord and cfg_EmitOpOperand in wishd201.exe. It has since
   been confirmed against the driver-side interpreter, drv_ScriptExecute at
   00017b90 in wishk201.sys, which decodes every one of them. The semantics
   below are read out of that interpreter and are FACT, not inference.

   The machine is a stack machine with a register accumulator. Below, "acc"
   is the accumulator and "pop" is the value taken off the operand stack.

6.1.  Machine State

   +-------------+-------------------+----------------------------+
   | Item        | Location          | Notes                      |
   +=============+===================+============================+
   | code        | devext+0x1650     | devext+0x1648 words        |
   | variables   | devext+0x1654     | devext+0x164c dwords       |
   | stack       | vars + varcount*4 | hard limit 200 dwords      |
   | accumulator | register          | working value              |
   | PC          | register          | word index into code       |
   | budget      | devext+0x1670     | starts at 0x186A0 = 100000 |
   +-------------+-------------------+----------------------------+

   The instruction budget is decremented once per instruction and the quantum
   ends with status 10 when it reaches zero. That is the runaway-script
   guard, and it is the reason an infinite loop in a script does not hang the
   machine.

   Note for anyone reading the same code in Ghidra: the constant 0x186A0 is
   stored into devext+0x1670 by drv_ScriptLoad, and Ghidra renders it as
   drv_ScriptNativeCall because a function happens to exist at that address.
   It is the number 100000, not a function pointer.

6.2.  Pointer Tags

   Values that denote an address carry a 4-bit tag in the high nibble. The
   interpreter switches on it in opcodes 0x080 and 0x181.

   +------------+----------------------------------------------------+
   | Tag        | Meaning                                            |
   +============+====================================================+
   | 0x10000000 | address of code, a script function                 |
   | 0x20000000 | global variable slot, emitted by the compiler      |
   | 0x30000000 | address of a stack local, produced by opcode 0x192 |
   | 0x40000000 | native builtin id, see section 6.5                 |
   +------------+----------------------------------------------------+

6.3.  Instruction Set

   The MNEMONIC column is the original author's own name for each opcode,
   taken from cfg_OpcodeMnemonics at 00421610 in wishd201.exe - a 43-entry
   disassembler table the configurator carries. It confirms, independently of
   the driver, every semantic derived from drv_ScriptExecute.

   Opcodes with bit 0x100 set are followed by a 32-bit operand word. Bit
   0x400 marks an unresolved PC-relative operand at compile time and is
   cleared before download.

   +-------+-------+------------------------------------------+
   | Op    | Mnem  | Operation                                |
   +=======+=======+==========================================+
   | 0x020 | mem   | acc = vars[acc], load variable           |
   | 0x021 | mempp | post-increment, mem++                    |
   | 0x022 | memmm | post-decrement, mem--                    |
   | 0x023 | ppmem | pre-increment, ++mem                     |
   | 0x024 | mmmem | pre-decrement, --mem                     |
   | 0x040 | not   | acc = (acc == 0), logical NOT            |
   | 0x041 | bnot  | acc = ~acc                               |
   | 0x042 | neg   | acc = -acc                               |
   | 0x080 | calla | call through acc, dispatched by tag      |
   | 0x082 | ret   | pop a return address into PC             |
   | 0x093 | push  | push acc                                 |
   | 0x095 | pwap  | swap acc with top of stack (sic)         |
   | 0x110 | load  | acc = operand, load immediate            |
   | 0x170 | b     | PC += operand                            |
   | 0x171 | bt    | branch if acc != 0                       |
   | 0x172 | bf    | branch if acc == 0                       |
   | 0x181 | call  | call the immediate operand, by tag       |
   | 0x190 | stack | stack pointer += operand                 |
   | 0x191 | bail  | stack pointer += operand, unwind form    |
   | 0x192 | loc   | acc = (depth + operand) | 0x30000000     |
   | 0x230 | stors | pop value; vars[acc] = value             |
   | 0x231 | stora | pop index; vars[index] = acc             |
   | 0x250 | lshft | acc = pop << acc                         |
   | 0x251 | rshft | acc = pop >> acc, arithmetic             |
   | 0x252 | add   | acc = pop + acc                          |
   | 0x253 | sub   | acc = pop - acc                          |
   | 0x254 | mul   | acc = pop * acc                          |
   | 0x255 | div   | acc = pop / acc, status 5 if acc is zero |
   | 0x256 | mod   | acc = pop % acc, status 5 if acc is zero |
   | 0x257 | band  | acc = pop & acc                          |
   | 0x258 | bor   | acc = pop | acc                          |
   | 0x259 | bxor  | acc = pop ^ acc                          |
   | 0x260 | eq    | acc = (pop == acc)                       |
   | 0x261 | ne    | acc = (pop != acc)                       |
   | 0x262 | gt    | acc = (pop >  acc)                       |
   | 0x263 | lt    | acc = (pop <  acc)                       |
   | 0x264 | ge    | acc = (pop >= acc)                       |
   | 0x265 | le    | acc = (pop <= acc)                       |
   | 0x266 | and   | acc = (pop && acc)                       |
   | 0x267 | or    | acc = (pop || acc)                       |
   | 0x294 | pop   | acc = pop, discard top of stack          |
   | 0x9f0 | cont  | continue placeholder, backpatched to b   |
   | 0x9f1 | break | break placeholder, backpatched to b      |
   | 0xd91 | -     | scope reference, always with bit 0x400   |
   | 0xd92 | -     | load local, (index) | (depth << 16)      |
   +-------+-------+------------------------------------------+

   RESOLVED. Earlier revisions of this note could not say which C operator
   each code in the 0x250..0x267 block meant, because the bison rule numbers
   could not be mapped back to tokens. The mnemonic table answers it
   directly, and the answer matches the inference that was recorded: 0x250
   through 0x259 are the ten operators with a compound-assignment form, and
   0x260 through 0x267 are the comparison and logical operators.

   NEW. 0x191, bail, was not separately identified from the driver, because
   drv_ScriptExecute handles 0x190 and 0x191 in one range test and both
   adjust the stack pointer. INFERENCE: bail is the unwind used when break or
   continue leaves a scope, as distinct from the ordinary scope adjust.

   The two 0xd9x opcodes have no entry in the table, so the configurator's
   disassembler does not cover everything its own code generator emits.

6.4.  Status Codes

   +------+------------------------------+
   | Code | Meaning                      |
   +======+==============================+
   | 0    | still running                |
   | 1    | thread terminated            |
   | 2    | bad variable index           |
   | 3    | stack underflow              |
   | 4    | stack overflow               |
   | 5    | divide by zero               |
   | 6    | PC or address out of range   |
   | 7    | illegal opcode               |
   | 8    | unknown native builtin       |
   | 9    | sleeping, reschedule         |
   | 10   | instruction budget exhausted |
   +------+------------------------------+

   On any fault other than 1, 9 and 0xB the interpreter stashes the thread
   context and a full copy of the variable array at devext+0x1684 and
   devext+0x1688, then reports the fault through drv_QueueEvent with event type
   0x42. Those two buffers are exactly what IOCTL 0xb98c20f4 drains, so that
   command is a post-mortem dump of a faulted script, not a trace buffer.

6.5.  Native Builtins

   A call whose target carries the 0x40000000 tag is dispatched to
   drv_ScriptNativeCall at 000186a0. This is the scripting language's
   standard library, and the NAMES come from cfg_ScriptSymbolNames at
   004212a0 in wishd201.exe, which the compiler predeclares into its symbol
   table.

   +------------+-----------------+-------------------------------------+
   | Id         | Name            | Function                            |
   +============+=================+=====================================+
   | 0x40000000 | _button         | set or clear virtual button 1..16   |
   | 0x40000001 | _stick          | set stick absolute, clamped +/-1200 |
   | 0x40000002 | _stick_relative | move stick relative, same clamp     |
   | 0x40000003 | _key            | keyboard event, usage and state     |
   | 0x40000004 | _mouse_button   | mouse button event                  |
   | 0x40000005 | _mouse_relative | relative mouse movement             |
   | 0x40000006 | _mouse_absolute | absolute position, clamped          |
   |            |                 | 0..0xFFFF                           |
   | 0x40000007 | _exit           | terminate this thread               |
   | 0x40000008 | _time           | elapsed milliseconds                |
   | 0x40000009 | _sleep          | sleep n milliseconds, yields        |
   | 0x4000000a | _wake           | restart another thread by id        |
   | 0x4000000b | _kill           | kill a thread by id                 |
   | 0x4000000c | _fork           | spawn a thread, at most 30          |
   | 0x4000000d | _getpid         | this thread's id                    |
   | 0x4000000e | _stick_swap     | NO-OP in this driver                |
   | 0x4000000f | _set_rumble     | NO-OP in this driver                |
   | 0x40000010 | _debug          | emits event type 0x4D to user mode  |
   +------------+-----------------+-------------------------------------+

   _stick_swap and _set_rumble are accepted by the compiler and reach the
   driver, but drv_ScriptNativeCall falls straight through on ids 0x0E and
   0x0F. INFERENCE: declared for a revision that implemented them, or
   reserved and never finished. A script using them compiles and runs and
   does nothing.

   _debug explains event type 0x4D, which section 7.2 previously recorded as
   unidentified. It is the script's print statement, delivered to the
   configurator through IOCTL fn 0x818.

   The stick clamp of +/-1200 is the same logical range the joystick
   collection declares in the HID report descriptor, so a script writes
   directly in report units.

   The language is genuinely concurrent. A script can spawn up to 30 threads,
   sleep in milliseconds, and kill or restart its siblings. That is the
   machinery behind behaviour such as "hold A and it emits repeated mouse
   clicks": _fork a thread that loops with _sleep while the parent continues.

6.5.1.  Event Handlers

   The compiler also predeclares twenty handler names.
   drv_ScriptDispatchInput at 00017550 reads these out of the script's own
   variable array and spawns a thread for each one holding a tagged code
   address.

       variable slots 0x00..0x3F, one per N64 button bit, in bit order:

           on_a    on_b    on_z    on_s        bits 0..3
           on_du   on_dd   on_dl   on_dr       bits 4..7
           on_lrs  on_unk  on_l    on_r        bits 8..11
           on_cu   on_cd   on_cl   on_cr       bits 12..15

       slot +0x40  on_button   any button changed, two button words
       slot +0x44  on_stick    stick changed, old and new X and Y
       slot +0x48  on_begin    runs first on any change
       slot +0x4C  on_end      runs last on any change

   This list CONFIRMS the N64 bit order that ioctl-surface.txt section 7
   could previously only infer from the driver's button map. Bit 8 is named
   on_lrs, that is L plus R plus Start, the combination the controller itself
   reports as its reset bit, and bit 9 is on_unk. Those are exactly the two
   positions holding filler zeros in the button map.

   The entry point symbol is main. cfg_CompileScript looks it up and emits a
   call to it in the fixed epilogue.

6.6.  Language Features Rejected By The Compiler

   The grammar is a full C expression and statement grammar, but several
   productions raise an error in their action rather than emitting code.
   These message strings are the clearest statement of what the scripting
   language is not:

       00421144  "invalid key description"          action 0x03
       0042112c  "labels not supported"             action 0x57
       00421110  "case keyword not supported"       action 0x58
       004210f0  "default keyword not supported"    action 0x59
       004210d0  "switch keyword not supported"     action 0x69
       004210b4  "goto keyword not supported"       action 0x76
       00421490  "undeclared symbol"                cfg_EmitSymbolRef

   So the language has if, while, for, do, break, continue, function calls,
   threads and the full C operator set, but no switch, no goto and no labels.
   Variables must be declared before use.

6.7.  Control Flow Construction

   cfg_EmitLoop at 0040c800 in wishd201.exe builds every loop from four code
   fragments, namely init, condition, increment and body:

       [init]
       if a condition is present:
           if do-while:  0x170  jump over the body to the condition
           [condition]
           0x172  jump past body and increment when false
       [body]
       close scope, backpatching break and continue
       [increment]
       0x170  negative displacement back to the top

   break and continue are compiled as the placeholders 0x9f1 and 0x9f0 and
   rewritten into real 0x170 jumps by cfg_CloseScopeAndBackpatch once the
   loop extent is known. Neither placeholder survives into the downloaded
   stream, which is why the interpreter has no case for them.
7.  Input Events

   A script never writes a HID report directly. The native builtins post
   events onto a list, and once the quantum ends the scheduler drains that
   list through drv_DispatchEvents at 00015e70. This is the last link in the
   chain from script source to bytes on the wire.

   Events are 0x14-byte nodes appended by drv_QueueEvent at 00015e00:

       +0x00  flink      +0x04  blink
       +0x08  type       +0x0C  arg1        +0x10  arg2

   The type splits into two disjoint classes.

7.1.  Types 0 To 2 Become Real HID Input

   These are handled entirely inside the driver and never reach user mode.
   They are the mechanism by which an N64 button press becomes genuine
   keyboard or mouse input.

   +------+-------------------------+-----------------------+
   | Type | Handler                 | Produces              |
   +======+=========================+=======================+
   | 0    | drv_HidKeyEvent         | keyboard report, ID 2 |
   | 1    | drv_HidMouseButtonEvent | mouse report, ID 3    |
   | 2    | drv_HidMouseMoveEvent   | mouse report, ID 3    |
   +------+-------------------------+-----------------------+

   Type 0 takes a HID usage and a down flag. Usages 0xE0 to 0xE7 set or clear
   a bit in the modifier byte at devext+0x1724. Usages 0x04 to 0xA4 are
   inserted into or removed from the pressed-key array at devext+0x1725,
   whose count lives at devext+0x17CA. Usage 0 clears everything. The emitted
   report is:

       0x0D  0x02  <modifiers>  0x00  <ten key bytes>

   The leading 0x0D is a length, so the report proper is 13 bytes: report ID
   2 followed by the 12-byte payload. That matches the keyboard collection in
   hid-descriptor.txt exactly. If more than ten keys are held, all ten slots
   are filled with 0x01, which is the HID ErrorRollOver usage - so the
   descriptor's unusual ten-slot array is honoured, and overflow is signalled
   the standard way.

   Type 1 maintains three button bits at devext+0x1714. Type 2 accumulates
   running totals at devext+0x1718 for X, +0x171C for Y and +0x1720 for the
   wheel. Both emit the same five-byte form:

       0x05  0x03  <buttons>  <dx>  <dy>  <wheel>

   Again the first byte is a length, so the report is report ID 3 plus four
   bytes, matching the mouse collection. Both paths share the button byte, so
   a movement report carries the current button state and a button report
   carries zero movement.

   Reports leave through drv_SubmitHidReport at 00014de8, which takes a
   buffer whose first byte is its length.

7.2.  Every Other Type Is A User-Mode Notification

   drv_QueueUserNotification at 00015ae0 appends the node to a queue that
   lives on the singleton control device, reached as the Wish_NA1 symbolic
   link, not on the calling adapter and not per handle:
   drv_AcquireControlDeviceExt returns that one extension to every caller.
   The queue head is at extension+0x60, counted at +0x5C and capped at 99
   with the oldest dropped. Every controller posts into it and any waiter can
   receive any event. See ioctl-surface.txt section 1.2.

   +------+-------------------+---------------------------------------+
   | Type | Posted by         | Meaning                               |
   +======+===================+=======================================+
   | 3    | _mouse_absolute   | ABSOLUTE 16-BIT POINTER POSITION,     |
   |      | (0x40000006)      | 0..0xFFFF with 0x8000 the centre.     |
   |      |                   | The relative mouse collection cannot  |
   |      |                   | express this, so it is handed to user |
   |      |                   | mode to apply. See below.             |
   | 0x42 | drv_ScriptExecute | a script fault; arg1 is the           |
   |      |                   | interpreter status code from          |
   |      |                   | section 6.4                           |
   | 0x4D | _debug            | the script print statement; see       |
   |      | (0x40000010)      | section 6.5                           |
   | 99   | drv_NotifyInter-  | DEVICE INTERFACE STATE CHANGED.       |
   |      | faceChange        | Posted by both                        |
   |      |                   | drv_EnableDeviceInterface and         |
   |      |                   | drv_DisableDeviceInterface, so it     |
   |      |                   | signals arrival AND departure. A      |
   |      |                   | listener must re-enumerate to learn   |
   |      |                   | which.                                |
   +------+-------------------+---------------------------------------+

   TYPE 3 IS ESTABLISHED, and was marked INFERENCE in an earlier revision.
   Three independent sources agree. The driver clamps both arguments to
   0..0xFFFF. The shipped script @--Sample Absolute Mouse.ac tracks the
   pointer in variables declared `static int mx=32768, my=32768`, i.e.
   centred in that range. And another shipped script computes the argument
   directly as `x * 65535 / 2400 + 32768`, mapping the +/-1200 stick range
   onto the full 16-bit span.

   ONE LIMITATION WORTH CARRYING INTO A REPLACEMENT: a script cannot drive
   the mouse wheel. drv_DispatchEvents calls drv_HidMouseMoveEvent with the
   wheel delta HARD-WIRED TO ZERO, and _mouse_relative carries only two
   arguments. The wheel byte in report 3 therefore only ever leaves the
   driver as zero, and the running total at devext+0x1720 can only ever be
   written with zero.

   Delivery is an inverted call. IOCTL 0xb98c2060, function 0x818, arrives at
   drv_IoctlWaitNotification, which parks the IRP on the waiting list at
   extension+0x68 and returns STATUS_PENDING. drv_CompleteNotificationIrps at
   00015ba0 pairs a queued event with a waiting IRP, copies type, arg1 and
   arg2 as three
   DWORDs into the system buffer, and completes it with Information = 12.
   That is precisely the 12-byte output recorded for fn 0x818 in ioctl-
   surface.txt.

7.3.  The Complete Chain

   Putting every stage together, a single line of script becomes application
   input by this route:

       script source
         -> cfg_yylex / cfg_yyparse        (wishd201.exe)
         -> 32-bit opcode stream
         -> IOCTL 0xb98c20f0               download
         -> drv_ScriptLoad                 (wishk201.sys)
         -> drv_ScriptExecute              interpreter quantum
         -> drv_ScriptNativeCall           builtin, e.g. 0x40000003
         -> drv_QueueEvent                 event {type, arg1, arg2}
         -> drv_DispatchEvents             type 0, 1 or 2
         -> drv_HidKeyEvent etc.           build the report
         -> drv_SubmitHidReport            hand to hidclass.sys
         -> the application

   Nothing above the driver is involved, which is the property the
   replacement must preserve.
8.  Consequences For The Replacement Driver
   The bytecode is the real configuration format. A replacement driver must
   implement the same interpreter, or the existing configurator cannot drive
   it. Conversely, a replacement configurator must emit the same encoding.

   Instructions are 32-bit words with an optional 32-bit operand. Nothing in
   the stream is pointer-sized, so the format itself survives a 64-bit port
   unchanged, and so does the two-DWORD buffer header. The pointer tags in
   the high nibble, however, assume a 32-bit value: 0x10000000, 0x20000000,
   0x30000000 and 0x40000000 partition a 32-bit word, and a 64-bit port must
   keep script values 32-bit rather than widening them.

   Branch displacements are 16 bits and relative to the emit point, in words.
   A script long enough to exceed that range would break silently; the
   compiler does not appear to check it.

   On validation, the original is better than a first reading of the IOCTL
   suggested. The interpreter bounds-checks as it runs: PC outside the code
   array gives status 6, stack underflow and overflow give 3 and 4, an out-
   of-range variable index gives 2, division by zero gives 5, an unrecognised
   opcode gives 7, and an instruction budget of 100000 per quantum bounds a
   runaway loop with status 10. The operand stack is capped at 200 dwords. A
   faulted script is stopped and dumped rather than allowed to continue.

   What is NOT checked is the stream itself at load time. drv_ScriptLoad
   copies the opcode array in and begins executing it; there is no
   verification pass, no signing, and no check that the final instruction
   does not claim an operand. A decoder that trusts bit 0x100 for stride can
   therefore be walked one word past the end of the buffer by a crafted last
   instruction, and the per-instruction PC check only catches the jump that
   follows. Any modern port should validate the whole stream once at load
   time, which is cheap and removes the entire class.

9.  Open Questions
   - The six opcodes the interpreter decodes but the compiler was not seen to
   emit: 0x095, 0x171, 0x181, 0x192, 0x230 and 0x294. Which grammar
   productions reach them, if any.

   - The drv_QueueEvent event types 0, 1, 2, 3 and 0x4D used by the native
   builtins. These are how a script actually produces HID input, so decoding
   them closes the last gap between a script and a report.

   - The meaning of the flags word at buffer +0x04, sourced from
   DAT_0045b608, and whether the top two bits of the count dword are flags.

   - The symbol table behind cfg_ScriptEmit and the meaning of field [5], which
   is what the epilogue 0x110 instruction carries.

   - How the 16 per-button script slots relate to the 32 macro slots in the
   driver, which are programmed by a different IOCTL entirely.

   -  The scheduler around drv_ScriptExecute: drv_ScriptThreadAlloc allocates
   -  thread contexts, drv_ScriptThreadQueue queues them and
   -  drv_ScriptScheduler drives the timer at devext+0x1690.
