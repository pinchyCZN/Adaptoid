                           ORIGIN MAP


Abstract

   Where every function in the replacement driver came from. THE DATA IS IN
   origin.tsv, one tab-separated row per correspondence; this note explains
   what those rows mean and records the cases that are not one to one.

   It exists so that when the reconstruction misbehaves you can get back to
   the evidence in Ghidra without guessing. Function names have already
   diverged - core_pak_addr_crc5 was drv_N64PakAddrCrc5 - and no naming rule
   recovers that.

   It is a file rather than a tag in a source comment so it stays out of the
   code, and so it can be diffed, grepped and mechanically checked.

   THE ADDRESS IS THE DURABLE KEY, not the name. The binaries in decomp/ are
   immutable primary evidence and are never rebuilt, so an address cannot rot.
   A Ghidra function name can still be changed by later analysis.

1.  The Format

   Six tab-separated fields:

       function    the name in src_drv
       file        the .c file it is defined in
       kind        port, part or new; see section 2
       binary      wishk201.sys, wishd201.exe, wishh201.dll, or - for new
       addr        eight lowercase hex digits, or - for new
       original    the Ghidra function name, or - for new

   A function may have SEVERAL ROWS. That is the normal case, not an
   exception: one replacement function can cover several originals, and one
   original can split across the core seam into two replacement functions.

   The binary field exists because there are three original binaries and a
   name can plausibly appear in more than one. Everything mapped so far lives
   in wishk201.sys.

2.  Kinds

   +------+------------------------------------------------------------+
   | Kind | Meaning                                                    |
   +======+============================================================+
   | port | This function is the replacement for that original, one to |
   |      | one. Going to the address answers the question.            |
   | part | It covers part of that original, or one of several. There  |
   |      | may be more than one row for the same function.            |
   | new  | No original. Scaffolding, or a harness stub standing in    |
   |      | for something Windows provides. Nothing to go back to.     |
   +------+------------------------------------------------------------+

   Everything in harness.c is new by construction: it stands in for the
   operating system, which is not in any of the three binaries. The kernel
   routines there carry their real Windows names, so a row like
   ExAllocatePoolWithTag means the HARNESS STUB of that name, not an original.

   A kind of port does NOT mean the body is finished. Parts of the tree are
   still stubs; the row records where the behaviour is specified, which is
   exactly what is wanted while writing it.

3.  Entries That Are Not One To One

   Worth understanding, because they are the shape most future entries take.

   drv_SubmitHidReport AT 00014de8 SPLITS ACROSS THE CORE SEAM. That single
   original does two things: it gates the report on drv_VirtualDevicesMask,
   tested as 1 << (reportID - 1), and then it delivers - either handing the
   report to a waiting read IRP or queueing it. The gate is OS-free and lives
   in core_emit; the delivery touches IRPs and lives in AdaptoidReportSink.
   So one original, two rows, in two different files. Splitting it is the
   whole point of the seam, not an accident of translation.

   drv_CompleteReadReport AT 00014ec0 is the other half of that delivery and
   is therefore a second row for AdaptoidReportSink.

   AdaptoidVendorSubmitUrb HAS TWO DEFINITIONS AND ONE ROW. It is the OS
   edge of the vendor transport: wdm.c defines it for the driver build and
   harness.c defines it for the harness, selected by ADAPTOID_USERMODE. Only
   one is compiled at a time, and both stand for the same original,
   drv_SubmitVendorUrb at 00019527, so the single row naming wdm.c covers
   both. The checker sees one definition per build and is satisfied either
   way.

   drv_BuildJoystickReport AT 00015150 IS ONE ORIGINAL AND SEVERAL ROWS. It
   decodes the stick, maps the buttons, packs the report, starts the
   accessory probe and implements the on-controller tuning mode, all in one
   function. The replacement splits the first three into core_decode_stick,
   core_decode_buttons and core_pack_joystick, with core_decode and
   core_on_raw_packet above them.

   core_tick HAS TWO ORIGINS because the original runs two independent
   engines off the same clock: the script scheduler at 00017980 and the
   effect ring at 00013ac0. Whether the replacement keeps them in one entry
   point is not decided; if it splits them, this becomes two rows against two
   functions.

   THE ACCESSORY PROBE is nine functions in the original, chained by
   completion routine: drv_AccessoryProbeStart, five Step routines, two Read
   routines and two Classify routines. The replacement is a state machine in
   a handful of functions, so the rows point at whichever original owns the
   behaviour rather than matching one for one.

4.  Keeping It Honest

       python tools/originmap.py --check    report drift, exit 1 if any
       python tools/originmap.py --fix      sort and normalise

   --check verifies that every function defined in src_drv/*.c has a row,
   that every row names a function that still exists and sits in the file the
   row claims, that the schema holds - six fields, nothing empty or
   space-padded, a known kind and binary, an address of eight lowercase hex
   digits - that a new row carries no address and a port or part row carries
   one, that no row is duplicated, and that the file is ASCII.

   That last check lives in originmap.py rather than asciify.py because
   asciify does not walk .tsv. Moving the data out of a .txt would otherwise
   have silently dropped it.

   --fix sorts by file, then function, then address, so rows land in a
   predictable place and diffs stay stable. It REFUSES to sort a file with
   malformed rows rather than guessing what was meant.

   WHAT NEITHER CAN VERIFY is that an address still names the function the
   row claims. The Ghidra database is not reachable from a script here and
   decomp/ is not in git. Addresses are read out of the database by hand when
   a row is written, so the risk is a typo at entry rather than decay.
   Confirm a row in Ghidra when you are about to rely on it.

5.  Why Not An Aligned Table

   This started as an RFC table in this file and was moved out. The reasons
   are recorded because the same trade-off will come up again.

   The table was 51 PERCENT PADDING, and the +---+ separator lines came to
   more bytes than the data they separated - about four bytes on disk per
   byte of content.

   Worse, the columns were fixed width with EXACTLY ONE CHARACTER OF
   HEADROOM. A new name one character longer than the current longest would
   have aborted the tool, and widening a column rewrites every row, so each
   such name churned the whole file. At a few hundred functions that does not
   work. A tsv row touches exactly one line and has no column widths at all.

   What the table was better at was being readable with no tooling, and
   being checked by asciify.py for free. The first is why this note still
   exists; the second moved into originmap.py, which is arguably the better
   home since it knows the schema.
